Git, explained from the object up

Most people use git the way people once used incantations: type this, hope, type it harder. It works until the first merge conflict, the first detached HEAD, the first force-push panic. The cure is not memorising more commands. It is knowing the three things any command can move — because once you can see what git actually stores, every command becomes obvious, including the frightening ones. This week I rewrote 169 commits on this site without changing a byte of content; that is only a sane thing to do if you know exactly what is underneath. Here is what is underneath.

The three things git can move

Every git command you will ever run manipulates some combination of exactly three places, and the documentation rarely says so out loud. The working tree is the folder you can see — ordinary files, the ones your editor touches. The index (the docs also say "staging area") is git's private draft of your next commit. And the history is a graph of commits, with a handful of named labels pointing into it, one of which — HEAD — marks where you are standing.

That is the whole machine. git add copies a file from the working tree into the index. git commit turns the index into a permanent snapshot and moves your branch label forward. git diff compares two of the three places. The commands that frighten people — reset, checkout, rebase — are frightening only because they move more than one of the three at once, silently. Learn the three places and you stop memorising commands; you start predicting them.

What a commit actually is

Git does not store diffs. It stores snapshots, whole ones, in a content-addressed object store — a small database living in the .git folder. A file's content is stored as a blob. A folder is a tree: a list of names pointing at blobs and other trees. A commit is a tiny text record that points at one tree — the complete state of your project at that moment — plus its parent commit or commits, an author, a date, and a message. Every one of these objects is named by a hash of its own content (SHA-1 in almost every repository you will meet). Change one character of a message and the hash changes, which means the "name" of a commit is its content. Nothing in the store can be edited in place, ever. Git only writes new objects.

Branches, which feel like heavy machinery, are the lightest thing in the system. A branch is a 41-byte file — .git/refs/heads/main — containing one commit hash and a newline. HEAD is another small file that usually says "I am on branch main". Creating a branch copies one hash into one file. That is why it is instant, and why the advice "branch freely" is not bravado — you are writing a sticky note, not copying a project.

Here is the receipt for the claim in the opening. This week I removed an unwanted trailer line from 169 commit messages in this site's repository. Because a commit's hash covers its message, all 169 commits got new names — and because a commit's tree is a separate object, I could verify with two lines of shell that every one of the 169 new commits pointed at the byte-identical tree as its original, with identical dates. The content provably never changed; only the envelopes were rewritten. Without the object model that operation is terrifying. With it, it is bookkeeping.

The everyday five

Ninety percent of git life is five commands, and each is one sentence once you hold the three places in mind. git status compares all three and reports the differences — that is its entire job, which is why it is always safe. git add file copies the file's current content into the index; edit the file again afterwards and the index still holds the older version, which surprises everyone exactly once. git commit -m "message" seals the index into a snapshot, makes it a commit whose parent is the current commit, and advances your branch label to it. Nothing you did not add goes in.

The two inspectors complete the set. git log --oneline --graph walks the parent pointers backwards from HEAD and draws the graph — it is how you see the structure you are standing in. And git diff answers "what is different?", but you have to know which two places it compares: bare git diff is working tree against index ("what have I edited but not staged"); git diff --staged is index against the last commit ("what am I about to commit"); git diff A B is any two commits. When a diff looks mysteriously empty, you are almost always asking the wrong pair.

Branching is free, merging is honest

git switch -c feature writes the sticky note and moves HEAD to it. Your next commits advance feature; main stays where it was. When the work is done, git switch main and git merge feature. If main has not moved since you branched, git notices your branch simply continues the line, and slides the main label forward — a fast-forward, no new commit at all. If both branches moved, git makes a merge commit: a commit with two parents, whose tree combines both sides. The graph records honestly that two lines of work happened and where they joined.

Conflicts are the moment git gets a reputation it does not deserve. A conflict means one thing: the same lines changed on both sides, and git refuses to guess. It writes both versions into the file between <<<<<<< and >>>>>>> markers and stops. Resolution is not a special mode with special commands — you edit the file until it says what it should, git add it to declare it resolved, and git commit. When one whole side is simply right, git checkout --ours file or --theirs file takes it in one move. The only conflict skill that matters is refusing to rush: the markers are a question, and the answer is a decision about the code, not about git.

Rebase writes new history and moves the labels

Remember that nothing in the object store can be edited. So what can "rewriting history" possibly mean? It means this: git computes what each of your commits changed, replays those changes one by one on top of a different starting point, writes new commits with new hashes, and moves your branch label to the new line. The old commits are not touched — they sit in the store, unlabelled, until they age out. git rebase main does exactly this to your feature branch, giving you the clean "as if I had started from today's main" line. git commit --amend is the one-commit version. Even my 169-commit rewrite was this same operation wearing industrial clothing.

Git never edits history. It writes new history and moves the labels.

This is also why the one iron rule of rebasing exists: never rewrite commits other people already have. Their labels still point at the old line; yours point at the new one; git sees two divergent histories and the "fix" usually merges the mess back together, doubling every commit. Rebase your own unpushed work as freely as you like. The moment a commit has been pushed to a shared branch, prefer revert — or accept the coordination cost and force-push with care, which is the last section's business.

The undo toolbox

Every undo situation is "which of the three places holds the mistake?" — and there is a tool per answer. Working tree only: git restore file overwrites the file from the index (destructive to your edit, invisible to history). Staged too early: git restore --staged file copies the index entry back from the last commit, leaving your file alone. Committed the mistake: now you choose between rewriting and recording.

What git reset actually moves. --soft moves the branch label only — your index and files stay put, so the undone commit's work sits staged and ready to recommit. --mixed (the default) also resets the index — the work stays only in your files, unstaged. --hard resets all three — label, index, and working tree — and is the only one of the three that can destroy work you have not committed.

git revert abc123 is the polite alternative: instead of moving labels backwards, it writes a new commit that applies the inverse of the old one. History records both the mistake and the correction, which is exactly what you want on anything shared. git stash parks uncommitted work on a side shelf so you can switch branches with clean hands, and git stash pop takes it back down. And git cherry-pick copies a single commit's change onto wherever you stand — the surgical tool for "I need just that one fix over here".

Then there is the safety net under all of it. git reflog is git's private diary of every place HEAD has been — every commit, switch, reset, rebase, and merge — kept for about ninety days even for commits nothing points at any more. Ran reset --hard on the wrong branch and watched a day's work vanish? git reflog, find the hash from twenty minutes ago, git reset --hard back to it. In a committed repository it is genuinely difficult to lose work permanently — the disasters people fear are mostly fifteen-second reflog recoveries. The corollary is the real rule of git safety: commit early, because only uncommitted work is ever truly at risk.

Sharing a graph with other people

A remote is just another copy of the same object store, and the collaboration commands are couriers between the two. git clone url copies the store and checks out a branch. git fetch brings down new objects and updates your picture of the remote — the origin/main labels — without touching your own branches, which makes it always safe. git pull is exactly fetch followed by a merge (or a rebase, if you tell it) of your branch onto that picture; when pull "goes wrong" it is the merge half, and everything from the conflict section applies. git push sends your objects up and asks the remote to move its label — and the remote refuses if you are not up to date, which is git protecting someone else's work from your label.

Overriding that refusal is what force-pushing is, and there is a right tool: git push --force-with-lease overwrites the remote branch only if it still points where you last saw it — a compare-and-swap, where bare --force is a blind overwrite that will happily erase a colleague's afternoon. When I force-pushed this site's rewritten history, the lease was the difference between "replace exactly the history I audited" and "replace whatever happens to be there". One more thing that week taught me: platforms keep their own labels into your graph — GitHub holds an immutable ref for every pull request ever opened — so treat rewriting as a tool for history you own outright, and expect the platform to remember some of the rest.

Reading about git is the weaker half of learning it. The stronger half is typing commands at a repository you cannot damage, watching the graph move — so I built one. The sixty-seventh game on this site is a terminal: a simulated repository, real commands, and nineteen missions that walk from git init to a capstone that uses the whole toolbox, with the graph drawn live as you type.

A safe repository, a real prompt, and nineteen missions from first commit to a whole-toolbox capstone. Break it freely — that is what it is for.

Play Git Quest

And if you want the object store explained by the person who has to live with the consequences, everything in this article is checkable against this site's own repository — 170-odd commits, every one of them a tree, a parent, and a label, exactly as described. That is the quiet beauty of git: it is not a tool you trust. It is a data structure you can check.
