Engineering practice

How I vibe coded this website — and the mechanism that made it hold

I did not hand-write most of this site. I described what I wanted, an AI produced it, and I kept the authority over every decision that mattered. That is the easy half to explain and the wrong half to copy. What actually made it survive is the mechanism I built around the prompting — how I specify, how I verify, and what happens when something breaks. This is that mechanism, with the receipts.

What vibe coding actually got me

Let me be honest about the starting point, because the honesty is the useful part. I described pages in plain English and a model wrote them. The first version of this site existed in an afternoon. If you have tried it, you know the feeling — it is genuinely fast, and the output is genuinely fine.

It is fine for about a week.

The trouble is not that the code is bad. The trouble is that you did not build a system, you accumulated one. Nothing records why the header is structured the way it is. Nothing stops the next change from quietly contradicting the last one. You cannot answer "is this still correct?" because you never wrote down what correct meant. Ask for one more feature and you get one more layer on a foundation nobody documented, including you.

As of writing (August 2026), this site is 186 pages — 62 of them browser-based labs that run real language runtimes, 67 games, 27 blog posts, the rest ordinary pages — across more than 160 commits, with zero npm dependencies, and it has only grown since. Nothing that size survives on vibes. What follows is the scaffolding that let it get there while I was still the one deciding.

The prompt is a specification

The single biggest change in my output quality had nothing to do with the model. It was realising that a prompt is not a wish. It is a specification, and it should be written like one.

"Make the blog look nicer" is a wish. It produces something, you squint at it, you ask again. Three rounds later you have drifted somewhere nobody chose. Compare that with what a real request looks like — the constraints first, the ask second:

What a usable spec contains. The goal in one sentence. The constraints that must hold no matter what. The things that must not change. How I will know it worked. And the cases I already know are hard.

On this site those constraints are permanent and I restate them constantly, because a model will cheerfully violate an unstated rule: the site must work with JavaScript switched off; no inline scripts, ever, because the content security policy blocks them; every page needs one h1, a canonical URL and a breadcrumb; the light theme is opt-in and every colour needs its light counterpart. That last one is not decoration — a token that looked right in dark mode once put near-white text on a near-white field in light mode, measured at 1.13:1, which is invisible while typing, on every form on the site.

State the invariants and you get work you can accept. Leave them implicit and you get work you have to re-litigate. The specification is not overhead you do before the real work — with a capable model on the other side, it is the work.

The repo remembers, the chat does not

Here is the failure I did not see coming. All the reasoning lived in the conversation. Why a value is what it is, what broke last time, which two approaches were tried and rejected — every bit of it sat in a chat log I would never open again. Six weeks later I would change something perfectly sensible and break something I had already fixed once.

So I made a rule: the reasoning goes in the repository, next to the thing it explains. The README is now 1,085 lines. The stylesheets carry roughly 1,650 lines of comments. Those comments do not say what the code does — you can read that. They carry the measurement, the rejected alternative, and what breaks if you change it back.

My favourite one is a note to myself about a tool I had written to regenerate the site's search index. The index had drifted out of date for months, and the comment explains exactly why:

A manual step with no command behind it is a manual step that gets skipped.

That single line has saved me more time than any prompt I have ever written. It is also the thing an AI cannot supply, because it is not knowledge about code — it is knowledge about what actually happened here, to me, on this project. The model is extraordinary at producing code. It has no memory of your project's scar tissue. Writing that down is your job, and it compounds: every future request you make can be grounded in it, and the next session starts informed instead of naive.

One pass is not a review

Generated code has a specific and dangerous failure mode: it is plausible. It reads well, it is confidently structured, and the bug is not a syntax error you would catch — it is a wrong assumption three levels down, wearing a convincing comment.

Reading it once yourself does not catch that. You are reading with the same mental model that wrote the request, so you see what you expected to see. What works is running several independent reviewers over the same change, each looking through a different lens — one for correctness, one for accessibility, one for what this breaks elsewhere, one whose only instruction is to try to prove the change is wrong.

The adversarial one matters most. A reviewer asked "does this look right?" says yes. A reviewer told "find the input that breaks this, and default to rejecting it if you are unsure" produces something useful. When several independent passes disagree, that disagreement is the signal — it is pointing at the part I had not actually thought through.

A real example from this repo. The deploy strips comments out of the stylesheets to make them smaller, and it needs to be certain it has not corrupted anything in the process. My first check counted braces before and after and compared them. Reasonable, obvious, and wrong — one stylesheet contains a comment that quotes a CSS rule, braces and all, so the check flagged a perfectly healthy file as corrupted. The fix was a scanner that understands comments properly, which also means a string containing /* can no longer be mistaken for the start of one. That bug was found by something actively trying to break the checker, not by me looking at it and nodding.

Make the build able to refuse

Review is a judgment, and judgment does not run at three in the morning when you are shipping a one-line change on your phone. The only thing that reliably protects a project is a check that runs every time and can say no.

So the deploy verifies its own output before it is allowed to succeed. It confirms 18 critical files are present and above a size floor, nine of them matched against an expected marker. It counts the HTML pages and refuses to continue below a floor of 80. It regenerates the search index from the pages so a deploy can never serve a stale one. Before writing a single byte of stripped CSS it checks that the ordered list of selectors is unchanged, that braces stay balanced, and that the output did not somehow grow. Any of those failing throws instead of writing.

The reasoning behind that is written at the top of the script, and it is the sentence I would keep if I could keep only one: failing the deploy is always safer than publishing the damage. A build that exits non-zero leaves the previous version serving. A build that cheerfully publishes a broken stylesheet does not.

This is the part people skip, and it is the part that makes AI-generated code safe to accept at speed. I am not carefully reading every line the model writes. I am making sure that if it is wrong in a way that matters, something mechanical catches it before a visitor does. I wrote about where to put that gate, and where the whole approach is a bad idea, in AI driven, human assisted — the short version is that you gate the irreversible effect, never the thinking.

When something breaks, ask for the diagnosis

Bugs are where the discipline either exists or does not, and the reflex is almost always wrong. The reflex is to paste the error, accept the patch, see the symptom disappear and move on. That works. It also teaches you nothing and leaves the actual cause in place.

What I do instead is refuse the patch on the first pass. I ask for the explanation: what is actually happening, why does it produce this symptom, and what are the candidate causes ranked by likelihood. Only when the account of the bug matches the behaviour I can actually observe does a fix get written. Roughly a third of the time the first confident explanation is wrong, and it is much cheaper to discover that in a paragraph than in a patch.

Then the same adversarial pass as before, pointed at the diagnosis rather than the code: try to refute this explanation. If it survives that, fix the cause and measure the result — not "looks better", but a number. Contrast ratios, byte counts, character-per-line measurements, the width at which a table starts overflowing. Numbers are the only way to know whether the fix worked or merely moved the symptom somewhere less visible.

And the last step, the one that turns a fix into an improvement: leave something behind so the bug cannot return silently. Sometimes that is a check in the build. Usually it is three sentences in a comment explaining what was tried and why it failed. A bug you fixed is worth a little. A bug that can no longer happen without something shouting is worth a great deal more.

This is just engineering

Read back what I have actually described. Write the specification before the code. Keep the reasoning next to what it explains. Have the work reviewed by people who did not write it, including someone trying to break it. Automate the checks so they run whether anyone is paying attention or not. Diagnose before you patch, and measure the fix. Leave the codebase safer than you found it.

None of that is new. It is the same discipline that has always separated software that lasts from software that merely runs. The only thing that changed is the implement — the typing is delegated now, and what is left is the specification, the judgment and the accountability, which was always the senior half of the job anyway.

So when someone says they vibe coded something, the interesting question is not whether an AI wrote it. Mine wrote most of this. The question is whether anything would have stopped it being wrong. If the answer is nothing, that is not a workflow — it is a bet you have not priced. Add the mechanism and vibe coding stops being a shortcut around engineering and becomes a genuinely faster way to do it.

Every claim here is checkable, incidentally. The site is static, the reasoning is in the comments, and if you want to see what the approach produces at the far end, the labs are 62 pages of real language runtimes and forensics tools executing in your browser with no server behind them.
