How to succeed in software development: the four-step path

After years of building systems and reviewing thousands of engineers, I've come to trust one simple order of operations. Great software isn't written in one heroic pass — it's grown through four stages: make it work, make it modular, make it readable, then make it optimized. The magic is entirely in doing them in that order.

Why the order matters more than the steps

Most people fail at software not because they can't do these four things, but because they do them in the wrong sequence. They optimize before it works. They polish readability on code they're about to throw away. They chase a perfectly modular architecture for a problem they don't understand yet. Each of those is effort spent in the wrong place at the wrong time. The four steps below are valuable precisely because they tell you what to care about now and what to deliberately ignore until later.

Step 1 — Make it work

The first and only job at the start is to get something running end to end, however ugly. One long function, hard-coded values, no error handling worth mentioning — fine. The goal here is not quality; it is proof. A working-but-messy version teaches you what the problem actually is, surfaces the surprises hiding in the requirements, and gives you something real to improve. A beautiful design for the wrong problem is worthless, and you can't know the right problem until something works.

The trap at this stage is perfectionism — polishing code you might delete once you understand the problem better. Resist it. Get to working first, and give yourself explicit permission for it to be rough.

Step 2 — Make it modular

Now that it works, you understand the problem well enough to see its natural seams. Modularity is the step where you break that one big blob into pieces that each do a single job — a function that only parses, a function that only validates, a function that only sends. Good modules have clear boundaries: you can understand one without holding all the others in your head, and you can change one without breaking its neighbors.

This matters far more in automation than people expect. A workflow built as one giant tangled step is impossible to debug when it fails at 3 a.m.; the same workflow split into distinct, named stages tells you exactly where it broke. Modularity is what turns "the whole thing is broken" into "step three is broken" — and that difference is everything when something goes wrong in production.

Step 3 — Make it readable

Code is read far more often than it is written, usually by a future version of you who has forgotten every clever thing present-you was thinking. Readability is a gift to that person. It means honest names that say what a thing is, functions short enough to grasp at a glance, and comments that explain the why a line of code can't express — never a restating of the obvious.

Clever code that only you can read is a liability, not a flex. The best code is boring: so clear that the next person understands it without asking you a single question.

Readability comes after modularity for a reason — it's much easier to write clear code for a small, well bounded piece than for a sprawling one. Once each module does one job, naming and clarifying it becomes almost easy.

Step 4 — Make it optimized

Only now, last, do you optimize — and only where it's actually needed. This is deliberately the final step because premature optimization is one of the most reliable ways to waste time and wreck the three things you just built. Optimizing before you have working, modular, readable code means you're speeding up something that might be wrong, entangling clean modules, and obscuring readable logic — all to fix a performance problem you haven't proven you have.

Do it properly: measure first, find the genuine bottleneck, and improve that one thing. Because your code is already modular and readable, optimizing is low-risk — you can tune one isolated piece with confidence, and the next reader can still follow what you did. The earlier steps are what make this one safe.

The same order works everywhere

This isn't only for code. It's how I approach an n8n automation, a research prototype, even a piece of writing: get a rough version working, break it into clean parts, make each part clear, then refine the parts that need it. The order encodes a mindset — earn the right to polish by first making something real, then make it easy to change, then make it fast. Rush to the end and you build something fragile. Walk the four steps and you build something that lasts, and that other people can build on.
