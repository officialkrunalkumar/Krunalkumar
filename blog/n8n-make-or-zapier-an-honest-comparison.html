n8n, Make, or Zapier: an honest comparison

I build automation for a living — HubSpot, n8n, Make and Zapier, in production, for clients who notice when it breaks. Most comparisons of these three are feature tables, and feature tables do not decide anything any more. The thing that decides it is where the workflow runs and who is liable when it goes wrong. Everything else is downstream of that.

The decision that actually matters

Open any of the three and you will find the same building blocks. A trigger. A branch. A step that calls an HTTP endpoint. A step where you can write JavaScript because the visual thing ran out of road. A library of prebuilt connectors for whatever software the client actually uses. The gaps between them are real but they are narrow, and they close a little every quarter, which is why a feature table written today is a stale document by the time somebody reads it.

Here is the column the feature tables do not have:

When this workflow runs at three in the morning, whose computer is it running on, and whose name is on the incident report if that computer is breached?

Zapier and Make are hosted products. There is no self-hosted edition, by design — the uptime and the connector maintenance are what you are buying. That means your client's records pass through a third party's infrastructure on every run, the run history sitting in that infrastructure contains the actual field values rather than a summary of them, and the OAuth tokens for every system you connected are stored there too. If your contract enumerates subprocessors, they go on the list.

n8n can be self-hosted. A container, a Postgres database, a machine you rent. Nothing about the workflow touches an intermediary at all. That is the entire argument, and it is the only argument that survives a conversation with a legal team.

Let me be fair before this reads as a pitch for self-hosting. That constraint applies to roughly one project in four. If nobody has mentioned data residency, nobody has a data processing agreement, and the payload is marketing emails, then a hosted vendor's security posture is almost certainly better than the one I would put together on a virtual server for a small client. Choosing self-hosted n8n for a five-step Zap-shaped job is not rigour. It is an unnecessary server for someone to forget about.

But get the order right. Answer the hosting question first, narrow to the tools that satisfy it, and only then argue about connectors and editors. Doing it the other way round is how a team ends up rebuilding nine months of workflows because a new client's security questionnaire asked one question nobody had thought about.

Where the workflow runs, and who is liable

Draw the same automation three times and the difference stops being abstract. It is one dashed box.

Three consequences that come up in real client conversations, in the order they come up:

  • Execution history is a copy of the data, not a log about it. This is the one people miss. Hosted tools keep run history so you can debug, and that history holds the real field values that passed through — the name, the address, the invoice line. If a run carries personal data, that data now also lives in a vendor's log store for whatever the retention window is on your plan. Check what that window is. On some plans it is a setting; on others it is fixed.
  • The credential store is one place holding keys to everything. An automation account usually ends up connected to the CRM, the mailbox, the file store and the billing system all at once. Whoever can open that account can act as all of them. Scope every connection down to what the workflow needs and no more — least privilege is not a formality here, it is the difference between one compromised token and a full-company incident.
  • Region is a question you will be asked. Make asks which data zone you want when you create the account, and moving afterwards means rebuilding in a new account rather than flipping a switch. n8n Cloud offers a region choice too. Zapier's public position has historically been its own infrastructure with residency options at the enterprise end of the pricing. Verify the current answer before you promise anything to a client — this is exactly the kind of detail that changes between when I write this and when you read it.

None of this makes hosted automation reckless. It makes it a disclosure. If you can name the vendor, name the region, name the retention window and show the connection scopes, you have a defensible answer for most clients in most industries. What you cannot do is pretend the question was not asked, and the shape of the obligations is the same one I set out in the compliance post.

The counterweight, stated plainly. Self-hosting is a promise you have to keep every month: patching the container, backing up the database, protecting the credential encryption key, renewing the certificate, restricting who can open the editor, and noticing when the disk fills. I have moved clients off self-hosted n8n and onto n8n Cloud, because an instance nobody has patched in a year is worse than the subprocessor they were avoiding. If nobody on the team can confidently run a container in production, self-hosting is not a security decision. It is a liability with a nicer story attached.

Work out what you are actually protecting first. Before choosing where a workflow runs, it helps to write down what it touches, who could reach it, and what the worst realistic outcome is. The threat modelling lab on this site walks that through as a structured exercise rather than a vibe, and it runs entirely in your browser.

Zapier: the one that works this afternoon

Zapier is the oldest of the three and it has spent that time on one thing: the shortest possible distance between a person having an idea and that idea running. You pick a trigger app, pick an action app, map a few fields, turn it on. There is no canvas to learn and no execution model to understand.

What it is genuinely best at:

  • Connector breadth. It is not close. The obscure scheduling tool your client's operations person insists on is probably in there, and probably with the specific action you need. Every hour you do not spend reading an API doc is an hour the project came in under quote.
  • A business person can read it. A Zap is a numbered list of steps in plain English. When the person who built it leaves, somebody in marketing can open it and work out what it does. I rate this far more highly than I used to, because most automation does not die of a technical failure. It dies because nobody left understands it.
  • The two-to-five step integration. Form submission creates a CRM record and posts to Slack. New invoice files a copy in Drive and messages the accountant. For this job — which is most jobs — Zapier is the best of the three and the argument is over.

Where it falls over:

  • Branching past a certain point. Paths work, and a Zap with three Paths and nested conditions inside them becomes something only its author can hold in their head. The vertical list that makes simple flows readable makes complex ones opaque.
  • Anything list-shaped. Handling an array of items is awkward, and it is billed per item, so the awkwardness has a cost attached.
  • Real transformations. The moment reshaping the data gets genuinely hard, you end up in a Code step — which means you have written code in a text box, with no local editor, no dependency management, no tests, and no way to run it outside Zapier to see what it does.
  • Reuse. Shared logic across Zaps is limited, so in practice you copy. Then you change one copy.
  • Change review. There is a version history that tells you a change happened. There is no diff a colleague can read, and no way to propose a change without making it.

Make: the one that draws the data

Make — Integromat, before the rename — puts the workflow on a canvas as connected circles, and the thing being drawn is the data, not just the order of steps. That distinction is the whole personality of the tool.

What it is genuinely best at:

  • Lists, properly. Iterators split an array into items, aggregators fold them back into one. Doing work per item and then collecting the results is a normal supported thing rather than a workaround, and if your data arrives as a bundle of line items this alone can decide it.
  • Debugging you can actually do. The execution history shows the input and the output of every module for a given run, as real JSON. When a client says "this one came out wrong on Tuesday," you can open Tuesday and see exactly which module produced the wrong shape. That is a meaningfully better answer than either of the other two gives you out of the box.
  • Error handling attached to the step. You can hang an error route off a specific module and say what should happen when that step fails — retry, ignore, take a different path, or park the run so it can be resumed after you fix the cause. That last one has saved me a full reprocessing job more than once.
  • Explaining it to a client. A canvas with routers on it is a picture you can put in a handover document, and non-technical stakeholders follow it.

Where it falls over:

  • The canvas turns on you. Somewhere past twenty modules the picture that was helping becomes a plate of spaghetti, and the layout is manual, so keeping it readable is unpaid work somebody has to keep doing.
  • The billing punishes its own strength. Operations are counted per module execution, so the iterators that make Make good at lists are exactly what makes the bill move. More on that below.
  • The expression language. It is capable, and you write it inside a small input box with a function picker. Anything longer than one line is unpleasant to author and worse to review.
  • Blueprints are exportable, not reviewable. A scenario exports as JSON, which is a real backup and a real way to copy a scenario between accounts. It is not a format designed for human review: identifiers and canvas coordinates churn, so a one-field change can produce a diff hundreds of lines long.

n8n: the one you can own

Start with the licence, because it is the most commonly misstated fact about n8n. It is source-available, not open source in the OSI sense. The Sustainable Use License — the company calls the approach fair-code — lets you read the source, modify it, and self-host it for your own internal business purposes at no licence cost. It does not let you host it as a service for other people or resell it without a separate arrangement. If you are an agency planning one instance with client workflows on it as a product, that sentence is the one to take to a lawyer before you take it to a landing page.

What it is genuinely best at:

  • Self-hosting, which is the point. A container and a database. Once it is running on infrastructure you control, the data residency conversation is finished in one sentence.
  • The workflow is a document. Export any workflow as JSON, commit it, review it in a pull request, restore it after a bad change. This single property is why n8n wins the maintenance argument later in this article, and it is not a feature the other two can add without changing what they are.
  • Code where you want it, nodes where you do not. A Code node sits in an otherwise visual workflow, so the eighty per cent that is plumbing stays visual and the twenty per cent that is genuinely logic is written properly. No other tool here gets that balance as right.
  • Sub-workflows. Real reuse. One "write this outcome back to the CRM" workflow that ten others call, fixed in one place.
  • AI orchestration. The model, tool-calling, memory and vector store nodes are ordinary parts of a workflow rather than a bolt-on, which is why I built CleverResponder, my open-source AI SDR, on it rather than on either of the others.

Where it falls over:

  • You own the uptime, in the boring literal sense. Upgrades, backups, certificate renewal, disk space, and the pager. If the workflow matters at 3 a.m., somebody has to care at 3 a.m.
  • Upgrades occasionally break workflows. You need a staging instance and the discipline to test on it, and most small teams have neither.
  • Fewer connectors. You will write raw HTTP requests against documented APIs more often than in Zapier. That is fine if you can read an API doc and a wall if you cannot.
  • Community nodes are somebody else's code. Installing one puts a third-party package inside the server that holds every credential you own. Treat it like adding a dependency to production, because it is one — the same supply chain question you would ask anywhere else.
  • The handover problem, inverted. A non-engineer can maintain a Zap. A non-engineer usually cannot maintain an n8n workflow with three Code nodes in it, and pretending otherwise at handover is how a project becomes permanently yours.

Three meters, and how each one surprises you

I am not going to quote prices. They will be wrong within months and they are the least interesting part anyway. What is worth learning is the shape of each meter, because each one surprises you in a different direction and the surprise arrives at scale, after the client has already committed.

Zapier meters tasks: one per action step that succeeds. Triggers do not count, and steps that stop the run generally do not either. The surprise is a multiplication people do not do in their head: a six-action Zap running a thousand times a month is not a thousand of anything, it is six thousand tasks. Teams budget on runs and get billed on actions, and the gap is exactly the number of steps they added after the first estimate.

Make meters operations: one per module execution, including the trigger. The surprise here is different and worse, because the multiplier lives in your data rather than in your workflow. One trigger that returns eighty line items, feeding an iterator, turns a single conceptual "run" into hundreds of operations — and the number changes daily with the size of the incoming payload. A scheduled scenario also consumes at least one operation each time it checks, whether or not there is anything to do, so a scenario polling every minute is spending all month finding nothing.

n8n Cloud meters executions: one per workflow run, however many nodes it contains. This is the shape that rewards big workflows, and it is genuinely liberating to add a node without doing arithmetic. The place the flat promise bends is sub-workflows, which can count as their own executions depending on how they are called — so if your design calls a sub-workflow per item in a loop, check that specific behaviour on your plan before you build it that way.

Self-hosted n8n meters nothing, which is the trap. The bill moves from a line item to a server plus your attention, and attention is the cost nobody puts in the quote. Budget the maintenance hours explicitly, write them into the proposal as a recurring number, and you avoid the slow argument that starts in month four — the same discipline as scoping any other work before quoting it.

Whichever you choose: build the real thing, run it for one real week on real volume, then read the tool's own usage counter. Multiply by four for the month, and double it for the retries and the growth you have not thought of. That number is the comparison. The pricing page is a work of fiction about somebody else's workflow.

One more shape worth naming: free tiers are sized for a demo. They are generous enough to prove the idea and never enough to run it, which is not a scam, it is the business model. The failure is quoting a project against the free tier and discovering the real plan in week three, after the price is fixed.

The maintenance question nobody asks

Every evaluation I have ever been handed compares what the tools can build. None of them compare what the tools cost to keep alive, which is where the money actually goes, because a workflow is not a thing you finish. It is a thing that decays as the systems underneath it change.

When the vendor changes an API

An endpoint gets deprecated, a field is renamed, an OAuth scope is split in two. Something in the chain will do this within a year — this is not a hypothetical, it is a Tuesday. The interesting difference is who picks the date.

On a hosted tool the vendor updates the connector for you, which is a real and underrated benefit — most API changes are absorbed before you ever hear about them. The cost is that a connector update can also change field names or output shapes underneath a mapping you wrote a year ago, and there is no version you chose and no tag to roll back to. On a self-hosted n8n pinned to an image tag, nothing changes until you pull a new image, which means you test the upgrade on staging and roll back if it breaks. It also means the fix waits for you. Neither column is free, and I would take the hosted behaviour for a simple integration and the pinned behaviour for anything load-bearing.

How you find out a run failed

  • Zapier. Errors appear in the history, and after repeated failures you get an email and the Zap is switched off. That last part is the one that hurts in practice: it stops quietly on Tuesday and you hear about it on Friday, from the client.
  • Make. Failed runs can be held in an incomplete-executions queue so you can fix the cause and resume the same run rather than reconstructing it, and error routes let you decide the behaviour per module. A scenario also deactivates after enough consecutive failures.
  • n8n. You can wire a single error workflow that catches failures from every other workflow and sends them wherever your team already looks, set retry-on-fail per node, and inspect the exact input and output of the node that failed. This is the one that behaves like software you operate.

The general point matters more than the differences: none of the three will page anyone unless you build the paging. The default everywhere is an email to whoever created the connection, who is frequently a person who has left the company. The first thing I add to any handover is a failure notification into a channel that a current employee actually reads.

Can you see what changed?

A workflow that a colleague edited last week is a change you did not review. What each tool gives you:

  • Zapier. A version history that records that something changed. Not a reviewable diff.
  • Make. A blueprint export that is diffable in the technical sense and unreadable in the practical one, for the reasons above.
  • n8n. Workflow JSON that a human can read. Node positions still churn and the diff is noisier than source code, but a reviewer can find the changed parameter. Git integration exists on the paid tiers; on a self-hosted community instance you export through the API in a scheduled job and commit the result, which is not elegant and is entirely sufficient.

Can somebody else take it over?

This is the question I would ask first if I could only ask one. Whoever inherits the workflow needs the credentials, some documentation, and the ability to read the thing itself. Choose for the person holding it in eighteen months rather than the person building it this week, and a surprising number of these arguments resolve themselves.

There is no migration path between them. A Make blueprint and an n8n workflow are unrelated formats describing different execution models, and Zapier has no comparable export at all. Switching tools means rebuilding by hand, re-authorising every connection and re-testing every branch. Price the choice as a two-year commitment, because that is what it is.

When the answer is none of them

Sometimes the honest recommendation is that this should not be a workflow tool at all. It should be two hundred lines in a repository, with tests, running wherever the rest of your software runs. The signs are specific:

  • The logic is the product. If what the workflow does is the thing the business sells, it belongs somewhere it can be reviewed, tested and owned properly.
  • You need tests. None of the three has a real testing story. You cannot assert "given this payload, this happens" and run it on every change. You test by running it and looking, which is fine for three steps and indefensible for thirty.
  • Volume makes per-unit billing absurd. Tens of thousands of records a day through a meter that charges per item is a rounding error in a database job and a line item that gets a meeting.
  • You need replay. Reprocessing a month of events, in order, without creating duplicates, is a normal requirement in code and a research project in a workflow tool.
  • More than about three branches of real business logic. A canvas is a poor way to draw a state machine, and a numbered list is worse.
  • Every node is a thin wrapper around code you would rather write. When the workflow is mostly Code steps joined by arrows, the visual tool has stopped paying for itself.

And the counterweight, because "just write code" is glib. Code needs somewhere to deploy, somewhere to keep secrets, monitoring, and a person on call — which is precisely the bundle the hosted tools are selling. If a team has none of that, moving the automation into a repository moves the problem rather than solving it. The reason I reach for code more often than people expect is that most teams I work with already have all of it for their own product, and the automation is the only thing living outside the system they already know how to operate.

When the answer is Apps Script

If every system involved is already Google — Sheets, Gmail, Drive, Calendar, Forms — then Google Apps Script is often the right answer, and it is the option nobody puts on the shortlist.

  • It runs inside the Workspace boundary. No new vendor, no new token stored on a third party's server, nothing crossing out of an account the organisation already trusts. In a compliance conversation that is sometimes the entire argument won in one sentence.
  • It is included. You are already paying for it. There is no task meter, no operation meter and no seat to add.
  • The triggers are enough for most of this work. Time-driven, on form submit, on edit, on open. That covers a large share of what small businesses build Zaps for.
  • It is code with version control. The clasp command-line tool pulls the project into local files, so you get a real editor, a repository and reviewable diffs — which is more than two of the three tools in this article can offer.

Where it stops, equally plainly. You are governed by quotas rather than by a bill: limits on how long a single execution may run, and daily caps on things like messages sent and external requests made. You do not get charged for exceeding them, you get stopped, which is a different failure mode to plan for. The moment a second SaaS product enters the picture you are writing raw API calls with no connector library, and one of the other three becomes the sensible answer. And the script tends to live in a place nobody looks, owned by whichever account created it — I have seen more than one useful script die quietly with an offboarded employee. Put the project in a shared drive, and commit the source somewhere the team can find it.

What I actually pick

Three questions, in this order, and I have never needed a fourth.

  1. Has anyone said "data residency", "processing agreement", "subprocessor", or named a regulation? If yes, the shortlist is self-hosted n8n or code, and the maintenance goes in the quote as a recurring line rather than a favour.
  2. Who maintains this in eighteen months? If the honest answer is somebody in the business rather than an engineer, it is Zapier — or Make if the flow genuinely branches. If the answer is a developer who will still be there, it is n8n.
  3. Does it repeat more than weekly, and does it touch anything irreversible? If so, put a human approval step in front of the irreversible part whatever you chose. That is the AI-driven, human-assisted pattern, and it is the same discipline I use for email reply automation: automation earns autonomy by being boring for a while first.

My default when nobody has answered any of those — which is most first conversations — is to build it in whatever the client already pays for. The second-best tool that someone in the room can maintain beats the best tool that only I can. That is not a compromise, it is the actual requirement, and it is the same reasoning I apply to choosing between AI tools: frequency and ownership decide more than capability does.

The one thing I will not tell you is which is cheapest, because nobody honestly can. The answer depends on the shape of your data rather than on anybody's price sheet, and the only way to know is to build one real workflow and read the meter for a week.

Questions people ask

Which one is cheapest?

Nobody can answer that from a price sheet, including me, because the three tools do not meter the same thing. A workflow with few steps and low volume is cheapest on Zapier. A workflow that fans one trigger out into dozens of items is punished hardest on Make and barely noticed by n8n. A workflow running constantly at high volume is cheapest as code on a server you already have. Build the thing, run it for one real week, read the usage counter the tool gives you, multiply by four, then double it for the retries and the growth you have not thought of yet. That number is your comparison. The pricing page is not.

Is n8n open source?

Not in the OSI sense, and the distinction matters commercially. n8n is source-available under the Sustainable Use License, which the company describes as fair-code: you can read it, modify it, and self-host it for your own internal business purposes at no licence cost. What you cannot do is host it as a service for other people, or resell it, without a separate commercial arrangement. If you are an agency planning to run one instance and sell workflows on it to clients, read the licence properly before you build the business model on it.

Can I self-host Make or Zapier?

No. Both are hosted products only, and that is a deliberate part of what they sell — the uptime, the connector maintenance and the security posture are the product. What they offer instead is a choice of region: Make asks which data zone you want when you create the account, and Zapier has published data-residency options at the enterprise end of its pricing. Neither is a substitute for the data never leaving your own infrastructure, so if a contract requires that, the hosted tools are out before you compare a single feature.

Does self-hosting n8n make me compliant?

No. It removes one subprocessor from the path, which can be the specific thing a contract asks for, and it hands you every obligation that vendor was carrying: patching the container, keeping the database backed up and encrypted, protecting the credential encryption key, restricting who can open the editor, and noticing when it stops. I have moved clients off self-hosted instances and onto n8n Cloud precisely because nobody was doing that work. An unpatched server you control is not more compliant than a maintained service you disclosed.

Can I move a workflow from one tool to another?

Not automatically. Make exports a scenario blueprint as JSON and n8n exports a workflow as JSON, but they are unrelated formats describing different execution models, and Zapier has no equivalent export at all. Migration means rebuilding by hand, re-authorising every connection, and re-testing every branch. Anything claiming to convert between them is doing a rough translation you will still have to check step by step. Treat the choice as something you live with for a couple of years, not a setting you can change later.

Which one should I use for AI agents?

All three can call a model API, so the real question is whether you want the tool to orchestrate the agent or just to make the request. n8n has the deepest native tooling for this — model nodes, tool calling, memory and vector store nodes as ordinary parts of a workflow — which is why I built my open-source AI SDR on it. Zapier and Make both have perfectly good AI steps for the common case of classify this, then draft that. What usually decides it is not the feature list but where the prompt and the customer record are allowed to travel.

How do I stop an automation bill from surprising me?

Learn what one run costs in the tool's own unit before you scale it, because each tool counts a different thing: Zapier counts action steps, Make counts module executions including the trigger, and n8n Cloud counts whole executions. Then find the multiplier that is specific to your data rather than to your workflow — usually an array that arrives with a variable number of items — and work out the worst realistic day rather than the average one. Put a usage alert on the account, and write the expected monthly figure into the quote so nobody is surprised in month three.

What about Power Automate, Workato, or the others?

The same two questions decide those too. Power Automate is worth a serious look when the organisation already lives in Microsoft 365, for exactly the reason Apps Script is worth a look when it lives in Google — the data does not leave a boundary that has already been accepted. Workato and the enterprise integration platforms sell governance, audit trails and support contracts, which is what a large compliance department is actually buying. I have kept this article to the three I ship production work in, because a comparison written from a marketing page is not worth reading.

The tools will keep converging, and half the specific behaviours above will have shifted by the time somebody quotes this back to me. The two questions underneath them will not, because they are about the work rather than the vendor: whose machine is this running on, and who will still understand it next year. Answer those and the shortlist writes itself.
