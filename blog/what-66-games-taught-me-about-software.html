What sixty-six tiny games taught me about serious software

The games page on this site looks like a break from the serious work. It turned out to be the serious work in miniature. Across sixty-six small games, every class of bug that matters in production showed up somewhere — inputs, state, persistence, promises — each one small enough to see whole and cheap enough to learn from. This is what they taught, with the receipts.

Why a security site ships Pac-Man

The games section shipped with sixty-six of them — Pac-Man and Tetris remakes, chess against three strengths of engine, seventeen terminal toys including one that does nothing but grow a bonsai tree. No ads, no accounts, nothing to install. A fair question is what any of that is doing on a consultant's website.

Part of the answer is that nine of them are security games. One deals you twenty emails and texts, half of them genuine, and makes you call each one — phishing practice with the reason given the moment you answer. Another lets you type a password and watch a real cracking run go after it: wordlist first, then mangling rules, then brute force. People who will not read a paragraph about password hygiene will happily lose to that game three times in a row, and the lesson survives in a way the paragraph never does. Play is the oldest teaching technology there is.

But the honest answer is the other one: building the games taught me more than building the serious pages did. A game is ordinary software with the difficulty turned up — real-time input, persistent state, an impatient user — and none of the forgiveness. Nobody files a bug report against a marketing page. Everyone notices when Pac-Man eats a ghost he has no right to eat.

Every bug in this article is real. Each one shipped, was caught by the adversarial review this site's build depends on, and is fixed now. What makes them worth writing about is that none of them is really a game bug. Each is a production bug class, caught small.

A game is a state machine wearing a costume

Strip the pixels off any of the sixty-six and the same skeleton is underneath: ready, playing, paused, game over. Four states, a handful of legal transitions, and every input the player can produce has to mean something sensible in all four.

The bug that taught me this had a nasty shape. Pause a run, then tap the board — the natural gesture for "carry on". The shell heard the tap, decided a tap means "go", and started a brand-new game. Your run — the score, the board, the twenty minutes — was gone. Not through a crash; through an input being routed by what it was instead of by when it arrived.

An input does not have a meaning. An input in a state has a meaning. A tap during play is a move, on a paused board it is "resume", on a dead one it is "again". The fix was to make the machine explicit — the shell now stamps its state on the page and every handler names the states it accepts — and the moment the state machine existed in code instead of in my head, the whole class of bug went with it.

If that sounds like a toy problem, it is the same defect as a checkout that submits twice because the button did not know the order was already placed, or a retry job that re-runs a payment because "clicked" was treated as "valid to execute". The costume is the only difference.

The keyboard is shared territory

This site has single-letter shortcuts — w and d switch the theme from anywhere, p pauses the background animation. They are useful, discoverable, and they were live while you played Hangman. Guess the letter w and two things happened: the game registered your miss, and the entire site switched to the light theme.

It is a comic bug in a game. It is also the same bug as a global hotkey swallowing what someone types into a search field, or two libraries both convinced they own Escape. A document-level listener is shared territory, and code that binds one is obliged to know what else lives there. The fix is two guards: if the key was aimed inside a game, or any run is live, the shortcut stands down. There is a reason accessibility guidance requires single-character shortcuts to be disableable — people using speech recognition trigger them with every word they dictate.

I would like to say the fix was complete on the first pass. It was not. The letters were guarded, and the one non-letter shortcut was missed — the full stop, which opens a controls panel, kept firing inside the typing trainer, whose passages are ordinary prose. The category of the bug was never "the w key". It was "a listener that did not know where it was", and a category has to be fixed as a category.

The input layer had one more lesson in stock. On phones, a tap on the on-screen controls arrived as pointerdown and then again as touchstart — two events describing one press, both bound, so every game with a pad played itself twice per tap. The repair is old wisdom wearing new event names: detect which model the browser speaks, subscribe to exactly one, and never bind both and hope.

Never save a state you would refuse to load

The 2048 board saves itself, so the run you abandon at breakfast is still there in the evening. That promise hid the most instructive pair of bugs in the whole section.

First: when a board was finished — no moves left — the game saved that too, and on your return restored it as a live game. Game over is checked after a move, no move was possible, so the restored board sat there immortal: not lost, not winnable, just stuck. Second: the New board button consulted the same saved state and politely dealt your old board straight back. The reset path and the restore path had quietly become the same path.

Never save a state you would refuse to load.

The durable fix was not at the save site but at the restore site. A snapshot is input, and it deserves the same suspicion as anything else that crosses a boundary. The restore now proves a board is actually playable before accepting it; a dead one is cleared and re-dealt. Anyone who has restored a session, opened a stale draft, or run a schema migration has met this bug in a bigger costume — old saved state is an input format, and you support it forever.

The copy is part of the specification

The chess page makes a specific claim: it plays every rule the game actually has. For a while that sentence was ahead of the code — threefold repetition was missing, so a perpetual check dragged on until the fifty-move rule ended it. The games hub advertised four strengths of engine; the page offered three. Snake's start screen promised WASD keys the shell never bound.

None of these breaks anything. There is no stack trace, no console error, nothing for a monitor to alarm on. The page simply makes a promise the code does not keep, and the visitor is the only test runner who will ever notice. A sentence on the page is a test the code has to pass.

Where a claim can be checked mechanically, check it mechanically. This site's build now cross-checks every game's advertised behaviour against its module the same way it checks that every share image exists — because a claim with no check behind it drifts, and prose drifts silently.

The fixes went in both directions, which is the point. Chess learnt threefold repetition, because the sentence was worth keeping. The hub's four strengths became three, because the code was right and the copy was boasting. Which side moves is a judgement — that there must be no daylight between them is not.

A canvas is a locked door

Every one of the sixty-six games draws into a canvas, and to a screen reader a canvas is a name and then silence. Score changes, the pause overlay, the game ending — none of it existed unless you could see it. Sixty-six games, and for a blind visitor not one of them could so much as say "game over".

The fix cost about a dozen lines, which is the embarrassing part. One polite live region in the shared shell announces what matters — paused, resumed, game over with the score, a new best — debounced so a score counter does not narrate every frame. Because it lives in the shell, all sixty-six games inherited it at once.

That is the lesson worth exporting: put the fix in the layer everything shares, or you will be making it sixty-six times — slightly differently, forever. It is the same reasoning as design tokens instead of scattered hex codes, or one auth middleware instead of per-route checks. Accessibility work in particular repays it: retrofitting one game is an afternoon, retrofitting a platform is a quarter.

The cheapest place to learn expensive lessons

A game that breaks costs a restart. That is precisely what makes the games section the right place to meet these bugs for the first time — the feedback is instant, the failure is visible to anyone who plays, and the cost of being wrong rounds to zero.

The bug classes do not stay in the games. Inputs routed without state, listeners that do not know their neighbours, saved state trusted on the way back in, prose making claims the code cannot honour, whole interfaces invisible to assistive technology — that list is what production incidents are made of, at ten thousand times the stakes. I met every one of them in miniature first, and the serious pages on this site are sturdier for it.

So the games page stays, and not as a break from the work. If you want the review mechanism that caught everything above, it is written up in how this site was built. If you would rather just lose to a password cracker for a while, the games are here — no ads, no accounts, and every rule the pages claim.
