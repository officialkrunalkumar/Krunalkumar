What build-gate failures taught me about CI

Every gate in this site's build exists because something shipped broken and nobody noticed — not in testing, not in review, and not in the deploy log. This is the six of them, the bug behind each, and what they changed about how I think about continuous integration.

Published 31 August 2026 · 9 min read · by Krunalkumar Shah

In this article

  1. The thing nothing else runs
  2. Two lists that must agree
  3. The gate that blamed the innocent
  4. Failures only strangers see

This site has no tests in the usual sense. It has gates: a build script that reads what it is about to publish, checks a handful of properties, and refuses to publish if any of them is false. There are six, and not one of them was designed. Each was written after something shipped broken and stayed broken, because nothing in the pipeline had any opinion about it.

That is the useful part. A gate written in advance is a guess about what might go wrong. A gate written after the fact is a description of what did. The six below are the second kind, and the pattern they share turned out to be more interesting than any of them individually.

All of this is readable. The gates live in one file, scripts/build.js, and every quotation below is a comment from it. The colophon explains the rest of how the site is put together.

Gate the thing nothing else exercises

Every page here carries structured data — JSON-LD blocks describing the page to search engines. Nothing on the page uses them. No visitor sees them, no script reads them, and no test could plausibly fail because of them. The build's comment states the problem exactly:

a JSON-LD block with a stray trailing comma renders identically to a valid one, and the only party that ever parses it is a crawler that silently drops it

Both halves matter. It renders identically, so review will not catch it. The only consumer fails silently, so production will not report it. Between those two facts there is no moment at which anybody finds out.

The gate parses every block on every page, the way a crawler would, and names the file if one does not parse. It is about fifteen lines. The reason it is worth having is not that JSON-LD is important; it is that this shape — invisible in review, silent in production — describes a whole category of artefact. Sitemaps, feeds, service worker manifests, robots files, structured data, share images. Nobody looks at any of them until a stranger does.

If I had to give one rule from all six gates, it is this one. Tests cover the code that runs. Gates cover the artefacts that do not.

Anywhere two lists must agree, one will drift

Three of the six gates are the same gate wearing different clothes. Each one is a case where a fact lived in two places and nothing held them together.

The sitemap parity gate holds the pages on disk equal to the URLs in sitemap.xml. It has two failure modes and both are silent: a new page that never made it into the sitemap is simply not surfaced to crawlers, and a sitemap entry whose page was deleted has crawlers requesting 404s under your own name. Neither shows up anywhere you would look.

The service-worker precache gate holds a hand-written file list equal to what the pages actually load. That list's own comment had already admitted the failure mode before the gate existed — “if a page grows a new stylesheet or script, it must be added here or offline quietly breaks” — which is a remarkable thing to write down and then leave to discipline. The gate turns that sentence into a refusal.

The static chrome gate is the starkest of the three. Every page ships a full static copy of the header and footer so there is something real before JavaScript arrives. The README asked for those copies to be kept in sync by hand, across ninety-odd pages. A link added to the canonical partial but not to the copies is invisible to exactly one group of people: those browsing without JavaScript — the people the static copy exists for.

Written out like that, the lesson is almost embarrassing. “Remember to update X” in a README is a bug with a delay on it. The delay is however long it takes somebody to forget, which on a good day is weeks. It is not a process problem and more discipline does not fix it; the only fix is to make one of the two lists derived from the other, or to make disagreement fail the build.

The gate that blamed the fifty-two files that were correct

The games on this site are described twice: once in a manifest that generates the pages, and once in the module that actually runs. Some fields appear in both. Where they disagreed, the manifest quietly lost — because nothing hands it to the runtime, so a value set only there is a comment that reads like code.

Three bugs shipped that way, and each one is a small lesson in how convincing a wrong file can look. Minesweeper recorded the slowest clear as its best score. Hangman's page said a stray tap could not cost you a guess; a tap spent a guess. Later, a racing game was found keeping its slowest lap as the record, because the module set the score key but not the sort order, so the shell's default of “higher is better” was applied to a lap time in seconds. The build's comment on that family is the sentence I keep coming back to: each looked correct in whichever file you happened to open.

So a gate was written to compare the two. And the gate was wrong. Its pattern was built by joining strings rather than written as a regular expression literal: 

new RegExp('\b' + field + '\s*:')

In a normal string, \b is not a word boundary — it is a backspace character. \s is just the letter s. The pattern matched nothing, so the gate concluded every game was broken, and the list of files it told you to go and fix was precisely the list of files that were already correct.

That is the most useful failure in the whole set, because it is a failure of the safety mechanism rather than of the thing it guards. The conclusion written above the fix is blunt: a gate whose own pattern is wrong is worse than no gate, because it sends you to fix code that was never broken.

Which leads directly to the rule I would now apply everywhere. A gate nobody has ever seen fail is a gate nobody knows works. The gates here are exported from the build script for that reason and no other — so they can be pointed at a deliberately broken copy of the site and proven to throw.

The failures only a stranger ever sees

The sixth gate checks that every share image a page declares actually exists. It sounds trivial. The failure it prevents is not.

A page pointing at a missing card does not fall back to a generic one. The crawler fetches the URL, gets a 404, and the link posts with no image at all. The build's comment describes where that leaves you: invisible locally, invisible in the deploy log, and only shows up when somebody shares the page, which is the one moment the image was for.

Sixty-six game pages had shipped in exactly that state. The generator emitted an image path for every one of them and not a single file had been rendered. Every page was correct, every link worked, the deploy was green, and every share was blank.

I think this is the most under-rated class of production bug. It is not that the failure is subtle; it is that the failure is invisible from inside. Nothing you can run on your own machine, and nothing the pipeline reports, is affected by it. The only observer is someone outside the system, at a moment you are not watching. Feeds, share cards, canonical URLs, redirects, robots directives, email deliverability and DNS all live in this category, and they are all worth a gate for the same reason.

What a gate owes you when it fires

Writing six of these changed my view of what a check should do when it trips. Three things, in order of how often they are got wrong.

Fail the deploy, do not warn. A warning in a build log is read once, by the person who added it. This site's gates throw and the deploy stops, with the phrase “refusing to publish” in the message. That is not severity theatre; it is the only setting at which the check reliably changes behaviour. A warning is a note to a future person who will not read it.

Name the file, and say what to do. Each gate prints the offending path and what is wrong with it. One of them goes further and simply performs the fix rather than demanding it — a fingerprint that used to fail the build and instruct you to edit two constants by hand now just writes the value itself. That is usually the better ending: if the gate knows enough to detect the problem, ask whether it knows enough to solve it.

Do not cry wolf. The games gate deliberately ignores values that merely restate the default, because flagging those would have produced dozens of correct-but-noisy complaints, and a gate that complains about seventy-eight things nobody needs to act on is a gate people learn to skim. Precision is not a nicety here. It is what keeps the check alive.

Where this does not transfer

I should be careful about how far to push this. These gates are cheap because the artefacts are files. Reading every HTML page on a small static site takes a second or two, so the whole check can run on every deploy with no meaningful cost, and there is never a reason to skip it or sample it.

That economics does not hold everywhere. On a large codebase the equivalent checks are slower, and slow checks get moved to a nightly job, and a nightly job is a warning again rather than a gate. I have not run this approach at that scale and I would not claim it transfers unchanged.

There is also a real failure mode in the other direction, which the wrong-regex story is one example of: gates are code, they have bugs, and a bug in a gate costs more than a bug in a feature because it is trusted. Adding a gate is adding something else that can be wrong. That is worth it when the thing it guards fails silently, and much less obviously worth it when the thing it guards already fails loudly on its own.

What I would carry to any project, at any size, is narrower than “write gates”. It is this: find the artefacts nothing exercises, and the facts that live in two places, and treat those two lists as your real risk register. On this site that turned out to be six items, and every one of them had already shipped broken before anybody went looking.
