When a static site outgrows being static

This site has no server. It runs real compilers, an operating system emulator and a forensics suite entirely inside the visitor's tab, which means "static" is nowhere near a synonym for "simple". It also has a ceiling, and the useful question is not whether you will hit it but which signal tells you that you have.

Published 31 August 2026 · 8 min read · by Krunalkumar Shah

Most arguments about static hosting are had at the wrong altitude. One side says static cannot do anything interesting, which is easy to disprove. The other says you never need a backend, which is not true either. The interesting question is narrower: which specific property forces the change, and what should you try before you accept it?

What static actually buys you

Worth stating plainly first, because the list is longer than people assume. There is no server to patch, so a whole category of vulnerability does not apply. There is no runtime to exploit and no database to inject into. The whole site sits on a CDN edge, so it is fast everywhere without you doing anything clever. It costs approximately nothing to run. And it is the same page every time, which makes it debuggable in a way a dynamic response is not: what you see is what everybody sees.

None of that requires the site to be simple. This one has zero dependencies in package.json — the figure is counted at deploy, not typed — and it still runs language playgrounds, a Linux terminal and a suite of forensics tools, all client-side. The heavy lifting moved to the visitor's machine rather than disappearing.

That relocation is the real trick, and it is also where the ceiling comes from. Anything that can be computed from what the visitor already has works beautifully. Anything that needs state the visitor does not have, or that must be kept away from them, does not work at all.

Offline is the capability people assume needs a server

One thing worth pulling out separately, because it is routinely given as a reason to move: a static site can work with no network at all, and it is not difficult.

A service worker sits between the page and the network, decides what to keep, and serves it back when there is nothing to serve from. On this site that means the document makers and every article keep working on a train, and a game you have opened once keeps working forever. Games are cached on use rather than up front, deliberately, so a first visit does not pay to download an arcade nobody opened.

The catch is the one every hand-maintained list has. The precached file list is written by hand, and its own comment admitted the failure mode before anything enforced it — if a page grows a new stylesheet or script, it has to be added there or offline quietly breaks. That is not an argument against the approach; it is an argument for deriving the list from the pages and failing the build when the two disagree, which is what happens here now.

The general point: reach for the browser capability before the server. Storage, offline, background sync, workers, WebAssembly and the file system access APIs have all quietly absorbed jobs that used to require a backend, and a lot of architecture decisions are still being made against a mental model of the browser from a decade ago.

The signals you have actually outgrown it

In rough order of how often they are the real reason:

  • Anything requiring a secret. This is the cleanest signal and the least negotiable. A key in client-side code is a public key, whatever it is named and wherever it is stored. If a feature needs a credential the visitor must not have, that feature needs a server. There is no clever workaround, only degrees of obfuscation.
  • Writes. The moment visitors create data that other visitors must see, you need somewhere to put it, a way to authenticate it, and a person to moderate it. Comments, accounts, uploads, a leaderboard. The storage is the small part; the moderation is what you are actually signing up for.
  • Personalisation. Two visitors needing different pages at the same URL is a direct contradiction of what static means. Some of this is faked well at the edge; most of it is not worth faking.
  • Freshness measured in minutes. If the content must be correct within a deploy cycle, and your deploy cycle is longer than the freshness requirement, that gap is the whole argument.
  • Editors who are not developers. If the people writing the content cannot or should not use the toolchain, you need a content system. That is an organisational signal rather than a technical one, and it is frequently the real reason a project moves.
  • Search that outgrows a shipped index. This site ships a prebuilt index and fetches it once, on first use, rather than on page load. It is currently about 957 KB across 272 pages. That is fine now and it will not be fine forever — the file grows roughly linearly with the site, and at some point asking for it becomes a worse deal than a query. When it does, the answer is a search service, not a bigger download.
  • Build times growing faster than content. If doubling the pages more than doubles the build, you have an algorithmic problem that will eventually decide the question for you.

Notice what is not on that list: complexity, interactivity, and volume of content. None of those force a server on its own.

The intermediate steps most projects skip

The common failure is treating this as a binary. It is a ladder, and most projects that “needed a backend” needed the second or third rung.

  1. A generator plus a gate. Where a fact lives in two places and drifts, derive one from the other and make disagreement fail the build. This site's games section is generated from a single manifest for exactly this reason, and its glossary works the same way. Very often this is not a step towards a backend — it is the whole answer, and the perceived need for a server was really a need for a source of truth.
  2. A build-time data file. If the data changes on your schedule rather than the visitor's, fetch it at build time and ship the result. Slow, expensive or rate-limited sources become free and instant this way.
  3. A service worker. Offline, caching strategy and background updates, with no server involved at all.
  4. One edge function. If a single feature needs a secret, give that feature a server and leave the other several hundred pages static. A form handler or a signed redirect is not an architecture change.
  5. A hosted service for the one dynamic thing. Forms, comments, search, authentication. Renting the part you need is usually better than building a backend to own it.
  6. A real backend. Correct when several of the signals above are true at once, and premature when only one is.

What you give up when you cross over

This is the half that tends to go unsaid, because the move is usually framed as gaining capability. You also acquire four things.

An attack surface. Everything that did not apply now applies: dependency vulnerabilities, injection, authentication bugs, and a patching obligation that never ends.

An availability dependency. A static site is down when the CDN is down, which is rarely. A dynamic site is down when any of its dependencies is down, and it now has several.

A bill that scales with traffic. Being linked somewhere popular changes from a nice day to an operational event.

The ability to make a simple promise. For this site that last one is decisive rather than incidental. Every tool here says nothing you paste is uploaded, and that claim is verifiable in a network tab precisely because there is nowhere for it to go. The moment a server exists, the promise becomes a policy — something you assert and the visitor takes on trust. That is a genuinely worse product for this particular site, so the ceiling is a feature and not a limitation I am working around.

The test worth applying

Not “is this hard to do statically?” — a great deal is hard and still worth doing, and the browser is a far more capable machine than the framing usually allows. The question that actually separates the cases is:

Does this need state that outlives the request, or a secret the visitor must not have?

If neither, it can almost certainly stay static, and the difficulty is an engineering problem rather than an architectural one. If either, no amount of cleverness on the client will get you there, and the honest move is to give that one feature a server rather than rebuild the site around it.

One caveat on all of the above, because it is a real limit on my confidence: this is a site run by one person where I own every decision and there is no editorial team, no compliance requirement and no revenue depending on a release date. Those constraints change the maths in ways I have not had to live with here, and I would weigh the organisational signals — editors, freshness, ownership — more heavily than the technical ones in most workplaces.
