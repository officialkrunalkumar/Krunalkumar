Why every number on this site is counted rather than typed

A number typed into a sentence is a claim with nobody responsible for it. It was true the day it was written, and nothing since has had an opinion about it. The fix is not discipline; it is to stop typing numbers into sentences.

Published 31 August 2026 · 8 min read · by Krunalkumar Shah

Every figure on this site — how many pages, how many labs, how many games, how many commits, how much CSS the build strips — is written into the page by the deploy, from what it just counted. None of them is typed. That started as a fix for one embarrassing page and turned into a rule, because the failure it prevents is worse than a wrong number.

The worked example is a page you can read. The colophon is a grid of figures about this site, and every one of them is recounted on each deploy.

Open the colophon

The failure is not a wrong number

A wrong number on its own is a small thing. The damage is what it implies about everything around it.

A page that says “62 labs” when there are a hundred and eleven does not read as out of date. It reads as maintained, because somebody clearly wrote a specific figure there on purpose. The reader has no way to distinguish a number checked yesterday from one checked two years ago, so they extend the same trust to both — and to the sentences either side of it.

That is what is actually being spent: not accuracy, credibility. And it is spent silently, because a stale number produces no error, no failed test and no complaint. The first person to notice is a reader, and they do not tell you. They just downgrade the site.

What actually drifted here

This is not hypothetical, and the repository keeps the receipts in its own comments.

The search index. The README had always said the committed index should be regenerated when page content changed, and there was no command to regenerate it with. By the time one was written, the index still described three pages as having no heading, still spelled a lab heading with a hyphen where the page had long since moved to an em dash, and carried the pre-edit title for another. The conclusion in that file is the general one: a manual step with no command behind it is a manual step that gets skipped.

One fact typed into six files. “Eleven language playgrounds” appeared on the home page, on the services page and on four lab pages, and “11 languages” three times more in the labs hub's own metadata. One fact, six files, and no mechanism by which any copy could notice it had gone wrong.

A comment about the build's own reach. One line described the work as covering “all 89 pages” until the output check started reporting 109. The comment now records both numbers, which is the honest way to leave it.

A count named by list instead of by number. A figure about the stylesheets said “the four stylesheets” while the list it referred to held nine, and later eleven. That one is instructive: the fix was not a better number but removing the number, and deriving the count from the list itself.

The mechanism, which is smaller than it sounds

A figure in prose is not written as text. It is written as an element with a key: 

<span data-count="labs">62</span> browser labs

On each deploy the build counts the labs on disk, finds every element carrying that key, and rewrites its text. The committed value is simply the last deploy's, so the repository copy is always a real number rather than a placeholder, and the next deploy corrects it.

Two details make it usable rather than merely clever. Figures can render as words, because the surrounding sentence is prose — “Eleven language playgrounds” reads better than “11 language playgrounds”, and a rewrite that turned every one into a digit would be a downgrade disguised as automation. And where the number lives in a meta description, where an element cannot go, the rule anchors on the words around the figure instead, so a reworded sentence stops matching and is reported rather than silently half-rewritten.

There is a third detail I find more interesting than the mechanism: count where the truth is. The figure for how many comment lines the stylesheets carry has to be read from git's copy of those files, not from the ones on disk — because by the time that code runs, the build has already stripped the comments out. Counting the wrong artefact would have produced a confident zero.

When you cannot count exactly, publish a bound and say so

The best part of this whole arrangement came out of it failing.

The colophon's commit count sat frozen at a hand-typed figure underneath a paragraph promising that every number on the page was counted at deploy. The reason was structural: the deploy platform clones the repository shallow, so a commit count taken there is the fetch depth rather than the history, and the branch that would have recounted never ran in the one place it mattered.

The fix has three parts and the third is the one worth stealing. Deepen the history first, then count for real. And when that cannot be done — no network, no credentials — publish a floor rather than either a lie or the fetch depth: the larger of what git can currently see and what the page already claimed, marked with a plus sign so it reads as “at least this many”.

That value never moves backwards, and it corrects itself upward on the first deploy that can reach the remote. It is the only thing still provable when the exact answer is unavailable, and it is honest in a way that a stale exact number is not. If you cannot count precisely, publish the bound and mark it as one.

Where counting cannot help you

This only works for facts derivable from the artefact. The build can count pages because the pages are right there. It can count dependencies, commits, stylesheet comments and games, because all of those are in the repository.

It can do nothing at all about a claim regarding the world outside. How many clients, how many people mentored, how many years of experience, how many projects delivered — every one of those is still typed by a human, still goes stale exactly as fast, and still has to be checked by a person who remembers to. The mechanism does not touch the numbers most likely to be wrong on a professional site, and I would rather say that plainly than let a page about counted figures imply otherwise.

There is a second limit worth naming. Some numbers should not be counted even when they can be. A count of games in a page's prose is accurate at every deploy and still misleading, because a total reads as a finished total — a claim about the section being complete rather than a measurement of how many things it holds today. Where a section is still growing, the honest move is to drop the figure rather than automate it, which is why some sentences here now say “every card below” instead of a number.

And one place the technique genuinely cannot reach: a recorded video. A figure spoken in a walkthrough, or captured in a screen recording of an interface that displayed it, is baked into the picture. No build step can rewrite that. The only options are re-recording it or saying out loud, next to the video, that the number has moved on — which is what this site does.

The general rule

Reduced to something portable, and none of it is specific to a static site:

  • A number in prose is a hardcoded value. Treat it the way you would treat a magic number in code — something with a source, not something you typed.
  • Derive it, or delete it. If you can compute it at build time, do. If you cannot, ask whether the sentence needs it. A great many do not.
  • Count the artefact, not a proxy for it. And be careful which copy you are counting.
  • Publish bounds when exactness is unavailable, and mark them.
  • Name the list, not the length. “The four stylesheets” goes wrong; a list that is checked against the disk cannot.

The version I would put on a wall is shorter. Nothing typed by hand stays true. That sentence is itself a comment in this repository, written after finding two files that disagreed about the same figure and were both right on the day they were written.
