Why “we don’t store your password” is usually false

The sentence is almost always false as stated and almost always true in the sense intended, and the gap between those two readings is where all of the security lives. Here is what is really in the row, how to judge it from outside without any access, and the one design that makes the claim honest.

Published 31 August 2026 · 9 min read · by Krunalkumar Shah

What the sentence is trying to say

Watch the one-way part first. The hash lab computes MD5, SHA-1 and the SHA-2 family in your own tab. Type a password, change one character, and watch the digest change completely — then look for any route back to the input. There is not one. That property is what the whole claim rests on, and it is worth seeing before we take it apart.

Open the hash generator

Almost every service you use says some version of it. We never store your password. Your password is never stored in plain text. Not even we can see it. It is usually said in good faith, and the thing it points at is real. Read literally, it is also false nearly every time it is written.

What they mean is that they store a hash. A hash function takes an input of any length and produces a fixed-length output called a digest. It is deterministic: the same input always produces the same digest. It is spread out: changing one character produces a completely different digest. And a cryptographic hash is built so there is no practical way to run it backwards — given the digest, you cannot compute the input that made it.

That is what makes a login possible without the plaintext. You type your password, the server hashes what you typed, and compares the result against the digest it holds. Equal digests mean you almost certainly typed the same string. The server checked your answer without ever having to read it.

So the literal reading — there is no column in the users table containing hunter2 — is usually true, and it matters. An engineer running an ad-hoc query sees digests. A backup that walks out of the building contains digests. A support agent who wants to be helpful cannot be.

The trouble is the step the sentence skips. A digest is not nothing. It is a deterministic function of your password and of nothing else, it is sitting in their database, and it is precisely the material an attacker needs in order to start guessing.

Why the sentence is still misleading

One-wayness and unguessability are different properties, and the sentence borrows the credibility of the first to imply the second.

An attacker holding your digest does not need to invert the hash function. Nobody does that. They guess. They take a candidate password, hash it with the same function, and compare. If it matches, they have your password — not something like it, the actual string you type. The one-way property stayed intact the whole time and was completely beside the point.

Determinism is what makes guessing cheap at scale. If the digests are unsalted, the same password produces the same digest for every user in the table, so one pass over a wordlist tests every account at once. And a fast hash is fast on purpose: MD5, SHA-1 and SHA-256 were designed for integrity checking, where digesting a large file quickly is the entire point. Speed is a feature there and a defect here.

“We don’t store your password” is a claim about a database column. What people hear is a claim about their safety after a breach. Those are not the same claim.

The honest version is longer and much less comforting: we store a value derived from your password, and we have chosen how expensive it is to guess your password from that value. That choice — the algorithm, and the cost dialled into it — is the whole question, and it is exactly the part the reassuring sentence leaves out.

If guessing rates feel abstract, the hash cracker lab runs the attack live in a worker on your machine with a guesses-per-second counter, so the rate you see is your own hardware rather than a number I quoted at you. It is a browser, so it is slow compared with rented GPUs. It is still instructive to watch a weak password fall over before you have finished reading the sentence that describes it.

The ladder of what is actually stored

“We hash passwords” covers an enormous range. Here is what is actually sitting in the row, ordered worst to best. Most real systems are somewhere in the middle, and the same reassuring sentence gets printed at every rung.

  1. Plaintext. The password itself, readable. It still happens, though usually in internal tools, legacy admin panels and log files rather than the main users table. There is nothing to say about it except that it is a failure.
  2. Reversible encryption. This is storing your password with an extra step. If the application can decrypt the value to check a login, anything holding the application’s privileges can decrypt it too — and the key usually lives in the same config file, the same environment, or behind a service the application may call whenever it likes. Encryption at rest defends against a stolen disk. It does not defend against a compromised application, which is how databases actually leak.
  3. Unsalted fast hash. MD5, SHA-1 or bare SHA-256. The value is genuinely one-way now, and it is also identical for every user who chose the same password — so the dump quietly discloses which accounts share a password, and one precomputed table cracks all of them together.
  4. Salted fast hash. A random per-user value mixed in and stored beside the digest. This kills precomputation and the shared-digest leak outright. What it does not do is slow anybody down: an attacker working on one account guesses at whatever rate the hardware allows, salt or no salt.
  5. Slow hash with a work factor. bcrypt, scrypt, Argon2. Deliberately expensive, with a cost parameter you turn up as hardware gets faster. scrypt and Argon2 also demand memory, which is what makes massively parallel cracking hardware awkward rather than merely expensive. This is the first rung where “hard to guess” has an actual dial on it.
  6. The same, plus a pepper. A secret value mixed in that lives outside the database — in the application configuration, or in a signing device the database cannot reach. If the database leaks and the application secret does not, the dump is useless. That is a narrow condition, and it also happens to be the most common shape of a breach: a dumped table, a stolen backup, an injection. Worth having, as long as nobody mistakes it for a replacement for the rung below it.

Rung two is where the sentence becomes flatly false. If the value can be decrypted, they are storing your password. Everything above rung two is an argument about how expensive guessing is. Rung two is an argument about who holds the key, and the answer is usually “the same server that just got compromised”.

The salt and rainbow tables lab builds rungs three, four and five in front of you: a lookup table filling up, that table cracking unsalted digests, a salt reducing it to nothing, and a fast-versus-slow comparison timed on your machine rather than asserted.

How to tell, from outside, without access

You will almost never get to read the schema. What you can read is the signup form, the reset flow and the emails, and those leak more than their designers intend. Here is what each signal is worth — separating the things that are proof from the things that are only a smell.

Signals visible from outside an account, and what each one actually supports. Only two of these are proof.
What you can observe What it actually tells you
A short maximum password length — 12, 16, 20 characters A hash is a fixed size whatever you feed it, so storage cannot be the reason. The cap suggests the password is being held or passed somewhere with a fixed width. A smell, not proof.
No spaces allowed, or “letters and numbers only” Hashing does not care which bytes you give it. A character-class ban suggests something in the path parses the password rather than hashing it. A smell, not proof.
An email that contains your password Proof. They stored it reversibly, or logged it at signup. Either way you are at rung one or two.
A “reset” that sends you your existing password Proof, for the same reason. Reset means set a new one. Recover means read the old one, and reading it requires having it.
“Must be different from your last five passwords” Not proof of anything bad — a careful implementation keeps the five old hashes and compares. It does tell you they retain password history, which is more derived data than most people assume is being kept.
Paste blocked in the password field Nothing about storage at all. It tells you their threat model ranks shoulder-surfing above password managers, which in my view is the wrong way round.

Two of those deserve a caveat I would want if I were on the other side of the table. bcrypt genuinely ignores input past 72 bytes, so a documented cap somewhere around 64 or 72 characters is an honest engineering constraint rather than a tell. A cap at 12 or 16 is not that. And a service that migrated recently may still be carrying an old validation rule nobody deleted, which is careless rather than damning.

There is one more test and it is the sharpest of them: truncation. Set a long password, then try to log in with only the first sixteen or twenty characters of it. If that works, the rest was thrown away and the strength you thought you had was imaginary. Do this only on an account you own, and expect to meet a rate limiter.

None of this reveals the algorithm. Nothing observable from outside does, unless the service publishes it or the code is open. If you want to know, ask — and read “we take security seriously” as the non-answer it is. In my experience a team that has done the work names the algorithm without hesitating, because they are quietly pleased about it.

Meanwhile the part you actually control is the password itself. The strength checker scores entropy and then subtracts for the patterns crackers try first, rather than awarding points for a capital and a digit, and it shows estimated crack times against four different hash types — which is the ladder above, expressed as time.

Where the claim is genuinely true

There is a family of designs where the sentence is not marketing. In an augmented password-authenticated key exchange the server stores a verifier, and logging in is a protocol that proves you know the password without the password ever crossing the wire.

SRP is the well-known one, and it is a genuine improvement: the server never sees the plaintext, not even at the moment you sign in, so a compromised server cannot sit there harvesting passwords as people log in. Be precise about what that buys, though. The stored verifier is still derived from your password, and a stolen verifier is still an offline guessing problem. SRP fixes the channel. It does not make the stored value uncrackable.

OPAQUE is the modern design in the same family, worked through the IETF crypto research group. Its improvement over SRP is roughly that an attacker cannot mount an offline dictionary attack from the stored record alone, because a per-user secret the server holds separately is needed to even begin. I have read the design rather than implemented it, so take that as a summary and not as guidance on parameters.

Passkeys are the ones that end the argument. A passkey is a public-private key pair. The private half stays on your device or in your platform’s keychain; the server keeps the public half and a credential identifier. There is no shared secret anywhere. There is nothing in that table that can be guessed into an account, because the value stored is meant to be public. A dump of a passkey credential table is close to worthless.

Passkeys are usually sold on phishing resistance, and that is a real property — the credential is bound to the origin, so a lookalike domain cannot use it. I think the breach argument is the stronger one and it gets made far less often: passkeys are the first mainstream login where “we do not store your password” is simply, boringly true. There is no password to store.

The limits, out loud. Passkeys move the problem to the device and to account recovery. If the recovery path falls back to a password, an emailed link or an SMS code, then the weakest of those is your real security and the passkey is decoration. I have gone through that trade in more detail in passwords, passkeys and what actually protects you.

“Passwords were hashed” tells you almost nothing

The same vagueness turns up in breach notifications, where it does more damage, because people make decisions from those emails.

“Passwords were hashed” is true of MD5 and equally true of Argon2id tuned to take a noticeable fraction of a second per guess. Those two sit at opposite ends of the ladder and imply completely different urgency: in one case the list is being cracked while you read the email, in the other it is a grind most attackers will not bother with. The word “hashed” does not distinguish them, which is presumably part of its appeal.

“Passwords were encrypted” is worse, because its ambiguity hides the failure. It might mean rung two, which is bad. It might mean whoever drafted the notice used “encrypted” loosely to mean hashed, which is common. The ambiguity is itself a signal: the person writing that sentence is not the person who built the system.

A good notification names the algorithm and its parameters — something of the shape Argon2id, 64 MiB of memory, three iterations, unique per-user salt. It also says whether the salts leaked, which they usually do and which is fine, because salts were never secret; and whether a pepper existed and whether it leaked too, because that last answer changes the whole picture.

What you should do is the same either way, and it is not really about their hash: change the password, and change it everywhere you reused it, because credential stuffing against your other accounts is the actual risk. How to read a data breach notification goes through the rest of that vocabulary line by line, and the breach check lab will tell you whether a password you are still using has appeared in a public corpus, using k-anonymity so that the password itself never leaves your tab.

What to say instead, and the limit of my argument

If you run a service, say the true thing. “Passwords are stored as Argon2id hashes with a per-user salt. We cannot read them, and the cost parameter is tuned so that guessing one is expensive.” That sentence is longer, it is checkable, and it commits you to something a reviewer can come back and test — which I suspect is most of the reason almost nobody writes it. A security review that meets the vague version will ask what is behind it, and the answer either exists or it does not.

If you use a service, the practical stance is short: assume the stored value is crackable, because for most services it is, and behave as though the breach has already happened. Long, unique, generated passwords in a manager. Passkeys wherever they are offered. A second factor where they are not.

Now the limit of my own argument, because it has a real one. Every rung of that ladder matters less as the password gets stronger. Against a genuinely random twenty-character password that appears in no wordlist, MD5 and Argon2 are both effectively unbreakable, because what stops the attack is the size of the search space rather than the cost of one guess. The ladder is doing its work for the large majority of passwords that are not like that — the reused ones, the dictionary ones, the ones with a birth year on the end.

So here is what would change my mind. If password managers became genuinely universal and every password in every database were random and unique, I would stop caring much which rung a service sits on, and I would find this article mostly beside the point. I do not expect that soon. Until then the sentence stays worth interrogating — not because the people writing it are lying, but because they are answering a question nobody asked. The question people actually meant is one clause longer: how expensive is it to guess my password from whatever you kept?
