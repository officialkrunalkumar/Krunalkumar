Writing comments that survive

The comment that goes stale is almost always the one that restates the code. The code moves and the sentence does not, and within a year it is actively lying. The comments that survive are the ones recording something the code cannot say for itself — and the best of them record a bug that was actually hit.

Published 31 August 2026 · 8 min read · by Krunalkumar Shah

In this article

  1. Why restating fails
  2. Put the measurement in
  3. Name the bug
  4. Rejected and load-bearing
  5. Admit the limit

“Comments go stale” is true often enough that a lot of people have concluded the answer is to write fewer of them. I think that conclusion skips a step. Some comments go stale quickly, some barely at all, and the difference is not how carefully they were written. It is what kind of fact they contain.

Every example below is from this repository, quoted rather than invented, because a post about honest comments written from imaginary comments would be a strange thing to publish.

Why restating the code is the one that rots

A comment that says what the line below it does has two problems. It duplicates a fact that is already expressed, precisely, in a language the computer checks — and it is coupled to the exact shape of that line, so any edit invalidates it. Nothing enforces the coupling, so the edit happens and the sentence stays.

A comment recording a reason is coupled to something much slower moving. The reason a decision was taken usually outlives several rewrites of the code that implements it. That is the whole argument in one sentence: reasons rot more slowly than mechanisms.

So the question to ask before writing a comment is not “is this clear?” but “is this something the code cannot already say?” There are four answers that reliably qualify, and they are the next four sections.

Put the measurement in

A number that came from measuring something cannot be argued with, and it dates itself honestly. The stylesheet on this site is full of them, because colour decisions are exactly the kind of thing that gets undone by somebody who thinks they are making an improvement.

One rule is annotated with the observation that white at sixteen per cent over the dark card measured 1.64:1. Another records a state that produced near-white text on a near-white field, measured 1.13:1. A third notes a panel position measured at 375 pixels.

None of those sentences explains what the CSS does; you can read that. They explain why the value is what it is, and they pre-empt the change somebody would otherwise make. If you are about to raise that opacity, you now know what you are undoing and roughly what it will cost. A comment that can stop a well-meaning regression has earned its space several times over.

Name the bug that was actually hit

This is the highest-value comment I know how to write, and it is the one people are most reluctant to write, because it means recording a mistake in a file other people read.

The EXIF reader on this site walks nested directories inside a photograph's metadata. A pointer in that structure is just a number out of the file, and nothing in the format stops it pointing back at the directory that contains it. The comment records what happened:

A JPEG whose 0x8769 tag pointed at its own IFD recursed until the stack gave out, and the RangeError had nowhere to go … the analyst was left with a permanently blank pane and no clue why.

Two guards sit under that comment, and it explains why there are two rather than one: a depth cap bounds nesting that merely goes too far, while a seen-set catches a cycle of any length, including a two-step one that a depth cap would only stop after eight laps. Without the comment, the second guard looks redundant and gets deleted by the next person tidying up.

The same file records a second one. The metadata stripper re-encodes an image through a canvas, and it was hardcoded to JPEG — so a PNG dropped in came back with its transparency composited onto black and every pixel put through a lossy encoder, for a tool whose entire promise is “the same picture, minus the metadata”. The comment names that plainly, then explains why the format is now decided by the magic bytes rather than the filename: the bytes are what the decoder actually saw.

A comment with a real failure in it gets read. That is not a small property. Most comments are skimmed; a paragraph that opens by admitting something broke is one people finish.

Say what you rejected, and mark what is load-bearing

Two more kinds earn their space, and both prevent a specific future waste of time.

The rejected alternative. The games engine here is a third shell alongside two that already existed, and its header spends a paragraph justifying that rather than assuming it is obvious — a visualiser runs forever and cannot be lost, whereas a game has runs that start, pause, end and produce a number worth keeping, and that single difference drags in a state machine, an overlay, a personal best and a thumb pad. Without that, the third file looks like duplication, and somebody eventually proposes merging it.

The load-bearing constraint. The same file has this, which is my favourite comment in the repository for its economy:

reset() BEFORE fit(), and this order is load-bearing.

It goes on to say what happened when the order was the other way round: the sizing pass ends by painting a frame, a game's draw reads the state that reset builds, and with the calls reversed Tetris drew a twenty-row grid that did not exist yet and threw on the first row. Two adjacent lines with no visible dependency between them — exactly the pair somebody reorders while tidying, with no reason to suspect anything.

Both of these are insurance against a specific, likely, well-intentioned edit. That is what makes them worth the words.

Admit the limit out loud

The last kind is a comment that says where the code is simplified, and it is the one that most changes how much I trust a file.

The database index lab here models query cost. Its header lists, in order, what the model does not do: the cost formulas are a cut-down version of a real planner's, indexes are modelled as freshly built and evenly packed where a real one churned for a year is looser and taller, and there are no visibility maps, no page cache, no prefetch and no concurrency.

That list costs the file nothing and buys a great deal. A reader knows immediately which results to trust and which to treat as illustrative, and a future maintainer knows which gaps were deliberate rather than overlooked — which is the difference between a simplification and a bug.

There is a version of this that also applies to gates and checks. The build here has a comment explaining that a check was deliberately narrowed so it would not flag dozens of harmless cases, because a gate that complains about things nobody needs to act on is one people learn to skim. Recording why a check is quiet is as useful as recording why it is strict.

The honest cost of writing this way

I should be even-handed about the downsides, because this repository is an extreme case and I would not defend all of it as a default.

The comment density here is high enough that the stylesheets are a substantial fraction comments by volume, and the deploy strips them out before publishing precisely because they are for whoever reads the source and not for the visitor downloading it. That arrangement works because the source is the artefact that matters and the delivered file is generated. Where you ship your source directly, the trade is different.

It also suits a codebase maintained by one person, where there is no review conversation to carry the context instead. On a team, some of what I write in comments would live in a pull request discussion, and a fair objection is that a long comment can be a substitute for clearer code. I do not think the two compete as often as that objection implies — you cannot express “this measured 1.64:1” or “a JPEG pointed at its own directory” in a better variable name — but the objection is right that the first move should always be to make the code say it.

And these still rot. A reason can be superseded; a measurement can be taken on hardware nobody uses any more. The claim is only that they rot more slowly, and that when one does go stale it tends to fail visibly — a story that no longer matches the code reads as strange, where a restated mechanism just reads as wrong and nobody notices.

The compressed version, if you want one rule: write the comment where the mistake would be made, and put the failure in it. Not in a wiki, not in a commit message nobody will run blame to find — on the line somebody is about to change.
