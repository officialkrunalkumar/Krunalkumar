Colophon

How this site is built

A colophon is the note at the back of a book saying how it was made — the typeface, the paper, the press. This is that note for this site: what it runs on, what it deliberately does without, and why. Every number on this page is counted at deploy time rather than typed, so none of it can quietly go out of date.

The stack

Hand-written HTML, and very little else

There is no framework here, no bundler and no build step in the usual sense. Every page is an .html file you could open in a text editor, and the file you see in the repository is the file the browser is served. package.json exists to name two scripts and a Node version floor; it has 0 dependencies, and nothing generated is committed.

That is a constraint rather than a boast. A site that outlives its framework is a site you can still change in five years, and most of what a framework buys you at this size is a rebuild you have to keep working.

Runs on

Static HTML, CSS and vanilla JavaScript. Vercel for hosting, with clean URLs and security headers set in vercel.json.

Does without

No framework, no bundler, no CSS preprocessor, no npm packages, and no cookie banner. Three measurement scripts run, all named in the privacy policy: one Google Analytics tag, Vercel Speed Insights, which times how fast the page rendered, and Vercel Web Analytics, which counts pageviews. Neither Vercel script sets a cookie.

Runs in your browser

The labs execute real language runtimes on WebAssembly locally, and nothing you type or drop into them is uploaded. The handful that look something up on the internet — DNS, RDAP, certificate transparency, breach and email-security checks — say so on the page and ask before they send anything. The privacy policy lists which, and to whom.

The deploy

A build that is allowed to say no

Pushing to main runs one script in a throwaway container. It strips the comments out of the stylesheets, rewrites the sitemap dates from git history, and rebuilds the search index from the pages so a deploy can never serve a stale one. Then it checks its own output before it is allowed to succeed: critical files present and above a size floor, the ordered list of CSS selectors unchanged, braces balanced, and the page count above a floor.

If any of that fails it throws instead of writing, and Vercel keeps serving the previous deployment. Failing the deploy is always safer than publishing the damage.

465 KB CSS in the repository
244 KB CSS on the wire
48% stripped at deploy

The difference is comments, and they are stripped in the container rather than deleted from the repository on purpose. Those comments carry the measurements — why a colour is the value it is, what broke last time, which two approaches were tried and rejected. Deleting them by hand to save bytes would trade the most useful prose in the codebase for a few kilobytes. Doing it at deploy keeps both: git keeps every comment, visitors get the smaller file.

Why it reads like this

The reasoning lives in the repository

The README runs to 1,510 lines, and the stylesheets carry roughly 3,317 lines of comments. They do not describe what the code does — you can read that. They carry the measurement, the rejected alternative, and what breaks if you change it back.

That habit is the whole method, and I wrote it up properly in How I vibe coded this website: the prompt as a specification, the reasoning kept next to the thing it explains, review by people who did not write it, and gates that run whether anyone is paying attention or not.

It is also why this page counts itself. A colophon that had to be edited by hand every time a lab was added would be wrong within a week — and a manual step with no command behind it is a manual step that gets skipped.
