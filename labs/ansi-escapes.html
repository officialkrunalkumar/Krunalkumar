ANSI escape codes, explained

An escape sequence is a handful of invisible bytes that tell your terminal to change colour, move the cursor, rename the window or write your clipboard. Paste some in and get every one named, dated to a standard and explained, with the result rendered beside it — then build your own, or defuse someone else’s.

  • Every sequence named, with its standard
  • SGR rendered, not merely described
  • Build one, copy it in five forms
  • A sanitiser for untrusted log text
  • Runs in this tab, nothing uploaded

Before you start

This tool runs entirely inside your browser. Nothing you paste or drop here is uploaded, logged or stored — which for security work is the whole point, not a footnote.

What it does not do

  • No uploads — there is no server to upload to
  • Not a terminal emulator: 80 columns, no scrollback
  • Private modes, OSC and device reports are explained, never obeyed
  • Colours shown are xterm defaults; your terminal has its own

Why that matters here

  • A log excerpt you paste stays in this tab
  • No raw escape byte for anything dangerous is placed on this page
  • Nothing you paste ever appears in your Network tab
  • Works with no internet once the page is cached
  • Free, permanently

Three things about escape sequences worth knowing

        

        

          

            
Colour vanishes in a pipe on purpose

            
A program that emits colour asks first. It calls isatty on file descriptor 1, and when standard output is a pipe or a file rather than a terminal, a well-behaved program emits no escape sequences at all. That is why ls | cat comes out plain and why grep loses its highlighting inside a script: nothing swallowed the colour, it was never written. --color=always removes the check, and the bytes then land in whatever you redirected into — which is how a log file ends up carrying ESC[01;34m in front of every path. Load the ls --color example above and the decoder will name every one of them, byte by byte.

          

          

            
NO_COLOR, and the conventions around it

            
NO_COLOR (no-color.org) has one rule and it is worth stating precisely: if the variable is present in the environment, colour is disabled, whatever its value is. An empty NO_COLOR= counts as set, which catches out people who expect 0 to mean off. The older neighbours are less tidy. CLICOLOR=0 asks for no colour; CLICOLOR_FORCE=1 demands colour even when stdout is not a terminal, which is the escape hatch for piping into less -R deliberately. TERM=dumb tells a program the terminal has no capabilities worth using. FORCE_COLOR is honoured across a great deal of Node tooling. None of them is universal — every program decides for itself, and a program that honours none of them is not violating a standard.

          

          

            
Escapes in someone else’s output are an attack surface

            
This is the part worth taking seriously. If an attacker can get bytes into a log you later cat, they control your terminal for the length of that file. Cursor movement and erase let them rewrite lines that have already been printed, so an entry reading DENIED can be replaced by one reading ok before you have finished reading the screen — run the first example and read the overwritten-character count under the render. OSC can rename your window, and window titles are text people trust. OSC 52 writes your clipboard with nothing changing on screen, so the next thing you paste into a root shell is theirs. Alternate screen and bracketed paste can be left in the wrong state, and bracketed paste turned off is the state in which a pasted newline runs the command. Terminal emulators have shipped real memory-safety and command-injection bugs in their OSC and DCS handlers as well. Nothing on this page executes any of it: the clipboard example decodes to a harmless string, and every dangerous sequence is shown inert.

          

          

            
What the renderer will and will not do

            
The render pane is a small screen model, not a terminal emulator, and it says so under every run. It carries out SGR, cursor movement, erase, insert and delete on eighty fixed columns, with no scrollback, no scroll region, no alternate screen buffer and tab stops every eight. Private modes, OSC, control strings and the device reports are named, explained and deliberately not obeyed — obeying ?1049 inside a div would mean nothing, and pretending otherwise would be the wrong lesson. The colours are xterm’s default palette, computed from the 6×6×6 cube and the 24-step grey ramp; your terminal ships its own, so treat every hex value printed here as a reference point rather than a promise about your screen.

          

        

      


      

        

          
Questions people ask

        

          

            Why does ls lose its colours when I pipe it into cat?
            
Because ls checks isatty on standard output before it emits any colour. Piped or redirected, stdout is a pipe or a file rather than a terminal, so a well-behaved program turns colour off. Nothing swallowed it — the escape sequences were never written. Passing --color=always overrides the check and writes them anyway.

          

          

            I used --color=always and now my file is full of [01;34m. What is that?
            
Those are the escape sequences themselves, sitting in the file as literal bytes. Each starts with a real 0x1B byte, which is invisible in most viewers, so you see the [01;34m and not the ESC in front of it. Paste a line into the decoder here and it will name every one, with its standard and its effect.

          

          

            How do I turn colour off for everything?
            
Set NO_COLOR. The rule from no-color.org is that the variable's presence disables colour whatever its value is, so even an empty NO_COLOR= counts as set. The neighbouring conventions are older and less consistent: CLICOLOR=0 disables, CLICOLOR_FORCE=1 forces colour on even when output is not a terminal, TERM=dumb tells a program the terminal can do nothing, and FORCE_COLOR is honoured by a lot of Node tooling. Support for each is per-program.

          

          

            Is running cat on an untrusted log file actually dangerous?
            
It is a real risk rather than a theoretical one. Cursor movement and erase let bytes in the file rewrite lines already on your screen, so a log entry can be made to lie about what happened. OSC can change the window title, and OSC 52 can write your clipboard, so the next thing you paste into a root shell is the attacker's. Several terminal emulators have also had memory-safety bugs in their OSC and DCS handlers. The sanitiser here shows you what is in a file before you let a terminal act on it.

          

          

            Does less -R make it safe?
            
No. The whole point of -R is to pass colour sequences through to the terminal, which means it passes the sequence through, and -r passes everything. Plain less with no flags is reasonable because it displays ESC[ instead of obeying it, and cat -v is closer to a safety measure because it makes every control byte visible. Neither is a security boundary. The durable fix is to strip control characters where the log is written, not where it is read.

          

          

            Why does my escape sequence work in bash but not in sh?
            
Usually two separate reasons. echo -e is not POSIX: bash and zsh builtins honour it, dash prints a literal -e, and /bin/echo differs again, so printf is the portable choice. And the backslash-e shorthand is a GNU extension, while backslash-033, the octal form, works everywhere. The builder here prints both command lines side by side so you can see the difference.
