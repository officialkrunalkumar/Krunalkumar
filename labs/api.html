Online API tester

Send an HTTP request and read the whole response — status, headers, timing and a pretty-printed body. The request goes from your browser straight to the address you type. There is no proxy in the path, which is unusual for a web-based API tool and is the reason nothing you send is logged in between.

Why some requests fail here and succeed in Postman

This catches almost everybody once, so it is worth understanding properly.

The browser is enforcing CORS

When a page requests a different origin, the browser only hands the response back if that server says it may — via an Access-Control-Allow-Origin header. Without it the request may well have reached the server and succeeded; the browser simply refuses to let this page read the reply. curl and Postman are not browsers and never had that restriction.

Which means a failure is information

If a request fails here but works from your terminal, you have learned something real: that API cannot be called directly from browser JavaScript. Anything you build for the browser will need a backend of your own in front of it. That is usually worth discovering early rather than halfway through a project.

Why there is no proxy

Every other browser-based API tester works around CORS by relaying your request through their server. That works — and it means your URLs, headers and any token you pasted pass through a machine you do not control. Not having a proxy is a deliberate trade: fewer APIs work, and nothing you send is seen by anyone but the API you addressed.

APIs that do work

Plenty of public APIs send permissive CORS headers — GitHub, httpbin, most open-data endpoints, and any API you have built yourself with CORS enabled. The examples in the picker above are all ones that work, so you can see the tool behaving before pointing it at your own.

Questions people ask

Why do some requests fail here but work in Postman?
Because a browser enforces CORS and Postman is not a browser. A browser will only hand a cross-origin response back to a page when the server sends an Access-Control-Allow-Origin header permitting it. curl and Postman have no such rule. So a failure here usually means the API has not opted in to browser access — not that the API is down.
Does my request go through your server?
No. The request goes from your browser straight to the address you typed. There is no proxy and no relay here, which is also why CORS applies — a proxy is exactly how other online API testers work around it, and running one would mean your requests, headers and tokens passing through someone else's machine.
Is it safe to paste an API key?
Your key is used only to build the request your browser sends, and it is never stored or transmitted anywhere else. That said, treat any key you paste into any web page as one that could be exposed — use a test key where you can, and revoke anything you would not want in a browser's memory.
Which methods are supported?
GET, POST, PUT, PATCH, DELETE, HEAD and OPTIONS. Bodies are sent for everything except GET and HEAD, which is what the HTTP spec expects.
Why can I only see a few response headers?
Another CORS rule: a cross-origin response exposes only a small safelist of headers unless the server names more in Access-Control-Expose-Headers. Same-origin requests show everything.
Can I test an http:// endpoint?
Not from here. This page is served over HTTPS, and browsers block mixed content, so a plain-HTTP request is refused before it is sent. Local development over http://localhost is the usual exception, but only from a page that is itself on localhost.
