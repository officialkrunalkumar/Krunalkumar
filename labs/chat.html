Peer-to-peer chat, and why a browser cannot listen on a port

Two browsers, one direct connection, nothing in between. This is as close as the web gets to netcat — and the ways it cannot get closer are the interesting part.

  • Direct browser-to-browser over WebRTC
  • No server relays your messages
  • No account, no database, nothing stored
  • Watch the ICE handshake as it happens
  • The only lab here that opens a peer connection
This lab uses the network. Most of the tools in Labs never open a network connection — that is their whole point. This one has to: it connects your browser directly to someone else's, which no other lab here does. Your messages are not stored anywhere and do not pass through this site, but they do leave your machine, and the person on the other end can read them. Treat it as a demonstration, not as a private messenger.

Why there is no “listen” button

netcat has two halves. One side listens on a port and waits; the other dials that address and port. A browser can only ever do the second. There is no JavaScript API that binds a socket and accepts an incoming connection — not a slow one, not a restricted one, none at all.

That is deliberate. A page that could listen would make every open tab a reachable server. Any site you visited could scan the tabs beside it, or address them directly, and a browser would become an attack surface the moment it was opened. The sandbox closes that door completely, and it is one of the more important doors it closes.

So how do these two find each other?

They cannot, unaided — which is why this lab asks you to carry the first message yourself. Each side writes a description of how it can be reached, and the two of you pass those descriptions between you over some channel you already share. After that the browsers talk directly, and nothing else is involved.

What STUN is doing

On the same wifi this works with nothing outside this page at all — both machines can see each other's local addresses. Across the internet each one is behind a router and does not know its own public address, so it asks a STUN server one question: what address do you see me coming from? That answer goes into the code you paste. No message ever travels through it.

Some networks defeat this entirely. If both sides are behind strict NAT, no pair of addresses works and the only fix is a TURN server that forwards traffic for you — which costs real money to run, so this lab does not have one. When it happens the page says so instead of spinning. Trying it on a different network, or both on the same wifi, usually works.

Questions people ask

Do my messages go through your server?
No. There is no server here to go through — the two browsers hold the connection directly, and no message is written anywhere. The only outside contact the chat itself makes is to a STUN server, which answers what public address you appear to come from and never sees a message. The page also loads analytics, like every page on this site: it records that a connection happened and whether a call was voice or video, never anything you sent.
Why is the code so long?
Because it has to carry everything the other browser needs to reach you: the ICE credentials, the fingerprint of your certificate, and up to eight of the addresses you might be reachable at. The page already drops the boilerplate lines of the handshake that do not vary between connections, and sends only the parts that do. Most of what is left is cryptographic randomness, which no encoding compresses. A short code would have to be looked up somewhere, and there is nowhere to look it up.
Why does it say “Could not connect”?
Both sides gathered addresses and no pair of them could reach the other, which usually means a strict NAT on one of the two networks. The fix is a TURN server that forwards the traffic on your behalf, and running one costs real money, so this lab does not have one. Put both machines on the same wifi, or try one of them on a different network. The page says so rather than spinning, because there is nothing else it can honestly do.
How big a file can I send?
That is the receiver's decision, not yours. When they press Accept, Chrome and Edge open a save dialog and write each chunk straight to disk, so the ceiling is their free space rather than their memory. Firefox and Safari have no such dialog, so they hold the file in memory and decline anything over 512 MB the moment it is offered, instead of accepting it and dying halfway through. Accept is a button because the save dialog will only open from a real click.
Can more than two people join?
Yes, for text. Everyone connects to the host and the host repeats what it receives, so each extra person is one more code exchange with the host and none with anybody else. That also means the host sees every message, since it is the thing doing the repeating. Voice and video stay one to one, because a browser cannot forward someone else's stream without decoding and re-encoding it, and that is the job a media server exists to do.
