How a database index actually works

Everyone is told an index makes queries fast. Almost nobody is shown the number that makes it true. So this lab counts: there is a 100,000-row table in your browser, laid out into 8 KB pages, with real B+tree indexes over it, and every query on this page reports the pages it actually read — with the index and without. Alongside it a live tree you can split and merge, so the shape doing the work is not a diagram in a book but something you broke yourself.

What you are actually looking at

The page counts are counted

A teaching tool that prints a plausible number next to a picture teaches that the number is decoration. So there is a real table here: 100,000 rows in typed arrays, laid out forty to an 8 KB page, and real indexes built by sorting the keys and packing them into leaves at a 70% fill factor. When a panel says the index read 462 pages, it walked the matching rows and asked which page each one lives on. Change the physical order of the table and the number changes, because the rows moved.

The tree really splits, and really merges

Insert into a full leaf and watch it split and copy a key upwards. Keep going and watch that propagate until the root itself splits and the tree gains a level — the only way a B+tree ever gets taller, which is why every leaf stays the same distance from the root. Then delete until a node drops below half full and watch it borrow from a sibling, or merge when there is nothing left to borrow.

Fan-out is the whole argument

The tree on screen holds three or four keys per node so a split is visible. A real index page is 8 KB and holds around 568 entries for a four-byte key, and that single number is why a billion-row index is four levels deep rather than thirty. The table under the tree runs the arithmetic at both scales side by side. Levels are page reads, and page reads are the thing you are paying for.

Composite order is a real decision

An index on (city, age) sorts by city first, so every row for one city sits in one contiguous block and every row for one age is scattered into twelve stripes. The strip in that tab draws the index exactly as it is stored, which turns the leftmost-prefix rule from a thing to memorise into a thing you can see. It is also why (city, age) and (age, city) are two different indexes.

Covering is a trade, not a free win

If the index holds every column the query asks for, the table is never opened and the plan is an Index Only Scan. Ask for one more column and every matching row gets fetched from the heap instead. You can tick columns on and off with the WHERE clause held fixed and watch the page count jump. The cost is on the same screen: each column added makes entries larger, so fewer fit per page and the index grows.

Where this model stops

The counting is real; the cost model on top of it is a cut-down PostgreSQL, and the plans are ranked by that model rather than by a real planner. There is no page cache, no prefetch, no parallelism, no visibility map and no concurrency, and the indexes are modelled as freshly built and evenly packed rather than churned for a year. Everything I simplified is named on this page rather than hidden behind a confident number.

Questions people ask

Are these page counts real, or a formula?
Counted. There is a 100,000-row table in three typed arrays, laid out into 8 KB heap pages, and there are real indexes over it built by a counting sort and packed into leaves. When a panel says the index read 462 pages, the tool walked the matching rows, asked which heap page each one lives on, and counted the reads. That is why switching the table to clustered order changes the number: nothing was estimated from a correlation coefficient, so nothing has to be re-estimated.
Is this PostgreSQL?
No, and the difference matters. The page counting is real. The cost model on top of it is a cut-down version of PostgreSQL costsize.c: seq_page_cost, random_page_cost, cpu_tuple_cost, and the same square-root interpolation a bitmap heap scan uses for its heap pages. Real planners have more terms, better statistics and parallelism. So read the chosen plan as what this model prefers, not as what your database will do. If you want the real thing, the Postgres lab runs an actual server in your browser.
Why does the planner stop using my index?
Because past a certain number of matching rows the index costs more than it saves. Following an index one row at a time means a seek per row, and on a table that is not physically ordered by that column those seeks land all over the heap. Once the query is going to touch most of the pages anyway, reading all of them straight through is cheaper, and the index becomes pure overhead on top. The last tab plots exactly where that happens on this table and lets you move random_page_cost to see the crossover shift.
What is the difference between an index scan and a bitmap heap scan?
An index scan walks the index in key order and fetches each row as it finds it, so it re-reads the same heap page every time two matching rows happen to share one. A bitmap heap scan collects every matching row pointer first, sorts them into physical page order, and then reads each page exactly once. That is why the plain index scan dies so early on this table and the bitmap plan keeps winning to a much higher selectivity. The folklore that an index stops being used above about five percent is really a statement about the first of those two plans.
Why is the B+tree in the first tab only three or four keys wide?
So a split fits on your screen. A real index page is 8 KB and holds hundreds of entries, which is why the table under the tree shows what the height does at production fan-out: a billion rows is four levels deep. At a fan-out of four the same billion rows would be fifteen levels, and every one of those levels is a page read. Drag the fan-out slider and the whole argument for short, fat trees is on screen in one move.
Does adding an index ever make things worse?
Always, for writes. Every index has to be descended and its leaf written on every insert, and roughly one insert per leaf-full also splits that leaf and writes two more nodes. The first tab counts the nodes each operation touches and shows the running average, and the table underneath turns that into pages written per INSERT for one, two, three and four indexes. An index that no query uses is not free and not neutral. It is a tax on every write you will ever do.
Why does SELECT * matter so much here?
Because it decides whether the table has to be opened at all. If every column you ask for is already in the index, the leaves answer the query on their own and the heap is never touched. Add one column the index does not hold and every matching row has to be fetched from the table. The covering tab lets you tick columns on and off with the WHERE clause held fixed, so you can watch the plan change from Index Only Scan to Index Scan and the page count jump, with nothing else different.
Does anything leave my browser?
No. There is no server, no upload and no network request of any kind. The table, the indexes and the tree are built in this tab and gone when you close it. That is not a privacy footnote so much as a design constraint: the point of the exercise is that the counting happens somewhere you can check it.
