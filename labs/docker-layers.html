Docker layer explorer

docker images says 1.6 GB for an application that is four megabytes of JavaScript, and the Dockerfile gives you no clue which line did it. So this prices every line. Edit the file on the left and the layer stack redraws with a size against each instruction — including the bytes a later rm did not actually remove, because it cannot. Every size here is a modelled estimate rather than a real build, which is the trade for it running entirely in your browser.

Before you start

This runs entirely inside your browser — the parsing, the size model, all of it on your own machine. Nothing is uploaded and there is no server.

Good to know

  • Sizes are modelled estimates, not a real build
  • Nothing is pulled, pushed or looked up
  • What you type is gone when you close the tab

Why it is here

  • A Dockerfile can carry more than you want to send anywhere
  • Works offline once the page is cached
  • Free, permanently

What you are actually looking at

A layer is a diff, and a diff can only add

This is the sentence the whole tool is built around. Every layer records what changed against the one below it, and the one below it is already committed and immutable. So a later layer can hide a file but never remove it, and the size of an image is the sum of its layers rather than the size of what you can see inside the container. The summary shows both numbers and the gap between them.

The secret you deleted is still in there

Copy a deploy key in, use it, delete it on the next line, and the image now contains a private key and a note saying it is not visible. That is not a subtle failure mode: docker save and tar are enough to get it back, and the Union filesystem tab prints the commands rather than gesturing at them. The naive Node example does exactly this so you can watch it happen.

Why COPY package.json comes first

A COPY is cached on a checksum of the files it copies, and everything after a cache miss rebuilds. Copy the whole source tree before installing dependencies and every one-line edit reinstalls them. The Cache tab lets you pick what changed and prices the rebuild, so the two Node examples answer the question with two numbers instead of an argument.

Built versus shipped

Multi-stage builds are usually explained as a style. They are arithmetic: layers in a stage that nothing copies from are written on the build machine and thrown away. The Go example writes about 1.1 GB across two stages and ships about 16 MB, and the summary keeps those two numbers side by side so the gap is visible rather than asserted.

The cleanup that cleaned nothing

apt-get update writes 42 MB of package lists. Deleting them in a later RUN buys you a whiteout marker and no space at all. Deleting them in the same RUN means they never reach a layer. The Python example splits update, install and cleanup across three instructions, which is how it usually gets written, and the tool prices the mistake.

Where the model stops

Sizes are estimates from a table, not a build. The parser does not do heredocs. Splitting a shell command on && ignores quoting. Packages I have no size for get a flat default, and commands I do not recognise contribute zero and say so in the layer detail rather than guessing. I would rather name all of that here than have you find it.

Questions people ask

Are these sizes real?
They are modelled estimates, and I would rather say that loudly than have you quote one in a meeting. Nothing here builds anything. The numbers come from tables in the tool: measured uncompressed sizes for the common base images, and typical installed sizes for the packages, wheels and dependency trees people actually install. They are close enough to tell you which line is costing you a gigabyte, and wrong enough that the only number worth trusting is the one docker images prints on your machine.
Why is the base image bigger here than on Docker Hub?
Because these are uncompressed sizes and the registry page shows the compressed download. node:20-alpine is about 55 MB to pull and about 135 MB once it is on your disk. Both numbers are true and they answer different questions: the compressed one is what your network pays, the uncompressed one is what your disk pays and what docker images reports.
I delete the file on the very next line. Is it really still in the image?
Yes. A layer is a diff and a diff can only add. The earlier layer is already committed, immutable, and possibly shared with other images, so a later layer cannot reach into it — all it can write is a whiteout marker saying the file is no longer visible. The bytes ship with the image. Anyone holding it can run docker save, untar the result, and read the layer blob with nothing more exotic than tar. The Union filesystem tab prints the exact commands. If a credential has ever been in a pushed layer, rotate it: squashing afterwards does nothing for anyone who already pulled.
So why does chaining commands with && actually shrink the image?
Because a file that is created and deleted inside one RUN never enters a committed layer at all. apt-get update writes 42 MB of package lists; if the rm -rf of those lists is a separate RUN, the 42 MB is already committed and you have bought a whiteout marker. Put update, install and the cleanup on one line joined with && and the layer is written once, without them. Load the Python example and look at the layer at line 7 to see the difference priced.
Why does COPY package.json before COPY . . matter so much?
The cache rule is one sentence: a step is reused only if every step before it was reused and its own inputs are unchanged, and for a COPY the inputs include a checksum of the files. Put COPY . . before the dependency install and every source edit changes that checksum, so the install runs again. Copy only the manifest first, install against it, then copy the source. In the two Node examples here that is the difference between a rebuild of about two minutes fifty and one of about forty-five seconds, on the same edit.
Do ENV and ARG leak secrets?
Yes, and this is the one that surprises people, because neither writes a byte to any layer. Both are stored in the image configuration that travels with the image, and docker history and docker inspect print them for anyone holding it. An ARG default counts too. Pass credentials at run time, or use RUN --mount=type=secret so the value exists during the build and is never part of the filesystem being committed.
What does this tool not understand?
Heredocs in RUN, which BuildKit supports and this parser does not. Character classes in glob patterns. Quoting, when it splits a shell command on && and ;. It also does not know your packages: an apt or apk package that is not in my size table is modelled at a flat default, and a command it does not recognise at all contributes zero and says so in that layer detail rather than inventing a plausible number. It checks nothing about known vulnerabilities, image signing or the runtime profile the container ends up with — those need a scanner and a running daemon, and this is a reading of one file.
Is multi-stage always the answer?
Not always, but it is the answer whenever the tools that build the thing are not the tools that run it. Go is the clearest case in the examples here: the build stage carries a compiler and a module cache and comes to about 1.1 GB, and the stage that ships carries a static binary on a distroless base and comes to about 16 MB. For an interpreted language the gap is smaller because the runtime has to ship anyway, and the win comes from leaving the compilers, headers and development dependencies behind instead.
Does anything leave my browser?
No. There is no server, no upload and no network request of any kind — not to a registry, not to a vulnerability database, not for a base image manifest. That is also why the sizes have to be modelled rather than looked up. Everything is in this tab and gone when you close it, and the page works with the network switched off once it is cached.
