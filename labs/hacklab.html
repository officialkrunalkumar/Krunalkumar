HackLab — break it to understand it

A deliberately vulnerable app you are meant to attack. The SQL injection runs against a real SQLite engine; the cross-site scripting really fires, and steals a token that is deliberately fake on a site with nothing real to take. Land the exploit, then read the fix — the half that matters.

  • Real SQL injection on a live engine
  • Sandboxed, genuinely-firing XSS
  • Path traversal, command injection, IDOR
  • Hints, solutions and the real fix for each
  • Nothing uploaded, nothing to attack but your own tab

Before you start

This is a hacking range: the targets below are meant to be broken. Everything runs in your own browser tab against throwaway, in-memory fakes — there is no server, nothing is uploaded, and the only thing you are attacking is a harmless sandbox on your own machine.

What this is

  • Real vulnerabilities, live, with objectives
  • The SQL genuinely executes in sql.js
  • The XSS genuinely fires, against a fake token
  • Hints and the real-world fix for each

What it is not

  • No real server, database or filesystem
  • No uploads, no network, nothing logged
  • Not a tool for attacking anyone else
  • Progress saved only on this device

Use what you learn here only against systems you own or are authorised to test. Doing this to someone else’s systems without permission is a crime in most places.

How this works, and why it is safe

Why a vulnerable-by-design app

You cannot really understand an injection until you have landed one. Reading that ' OR '1'='1 bypasses a login is abstract; watching it walk past a real query engine, live, is not. This is the same idea as DVWA or OWASP Juice Shop, minus the Docker container and the spare VM - it runs in the tab you already have open.

Everything runs on your machine

The SQL executes in sql.js in your browser. The XSS fires in a sandboxed frame in your browser. The traversal, command injection and IDOR run against in-memory fakes in your browser. There is no backend and no network call - a hacking sandbox that phoned home would rather defeat the point.

The fix is the deliverable

Each challenge pairs the break with its remedy, and the remedy is the part worth remembering. Parameterised queries, contextual output encoding, calling programs with an argument vector rather than a shell string, checking ownership and not just login - these are what actually stop the attacks you just performed.

Where to go next

The defensive side of these lives elsewhere in Labs: decode a token safely in the JWT tool, take a phishing link apart in the URL inspector, and read raw email headers in the header analyzer. HackLab is the offensive counterpart to that toolkit.

Questions people ask

Is this legal and safe to use?
Yes. Every target is a throwaway built in your own browser tab - a fresh in-memory SQLite database, a sandboxed iframe, in-memory fakes. There is no server, nothing is uploaded, and the only system you are attacking is a harmless one running on your own machine. Practising here is exactly what it is for.
Is the SQL injection real or simulated?
Real. It runs against sql.js - the same actual SQLite engine as the SQL lab - and your injection genuinely executes. The difference from attacking a real site is only that the database is a disposable one created in memory when you open the challenge.
How is the XSS challenge safe if the script really runs?
Two ways. The payload runs in a throwaway guestbook page served with a strict connect-src none policy, so it cannot fetch, beacon or websocket a stolen value out - it can only message it back to the challenge, which is how the solve is detected. And what it steals is a hardcoded fake token: this whole site is static, with no accounts, no secrets and no real user data, so even a flawless exploit walks away with a string that was never worth anything. That harmlessness, not any single sandbox trick, is what makes it safe.
Do I need to know how to code?
A little helps, but each challenge shows you the vulnerable query or command as you type, gives progressive hints, and reveals the full solution if you want it. You can learn the pattern by doing it.
Does breaking the challenge teach me anything defensive?
That is the actual point. Every challenge ends with the real-world fix - parameterised queries, output encoding, argument vectors instead of shell strings, authorisation checks. The exploit is the hook; understanding why the fix works is what you keep.
Is my progress saved?
Yes, in your browser's local storage on this device only. Nothing is sent anywhere, and you can reset it any time with the button in the challenge list.
