HTTP/1.1, HTTP/2 and HTTP/3, raced on the same link

Almost every explanation of these three protocols describes the differences. Very few show them, and the distance between “HTTP/3 handles packet loss better” and watching HTTP/2 freeze solid while HTTP/3 keeps running is the whole distance between a claim and an understanding. So this lab loads the same page three times at once, over one link whose latency, bandwidth and packet loss you set, and draws the three waterfalls side by side. The loss slider is the control worth playing with.

What each version actually changed

HTTP/1.1: one request at a time, per connection

A connection carries one request and waits for the whole response before the next one can go. Browsers worked around that by opening six connections per origin, so the seventh resource waits for a lane to free up regardless of how fast the link is. Pipelining was supposed to fix it and did not: middleboxes reordered or mangled the responses, so browsers shipped it disabled and eventually removed it. Sites shipped domain sharding instead — serving assets from img1, img2, img3 purely to buy more connections.

HTTP/2: one connection, many streams — and one queue underneath

HTTP/2 put every request on one connection as an independent stream, interleaved frame by frame, and compressed the headers with HPACK so the repeated ones stop costing anything. Six lanes became one lane carrying everything. What it did not change is what is underneath: a single TCP connection is a single ordered byte stream, so the streams are independent to the application and not independent at all to the transport.

HTTP/3: the streams moved below the ordering

QUIC is a new transport on top of UDP, and it puts the stream boundaries inside the transport rather than above it. Each stream has its own delivery order, so a lost packet blocks the stream it belonged to and nothing else. It also folds the transport and TLS handshakes into one flight, which saves a round trip on every cold connection, and it identifies connections by an ID rather than by your IP address, which is why it can survive you walking off the wi-fi.

The part nobody puts on a slide

Six TCP connections have six congestion windows and recover from loss six times as fast in aggregate as one connection does. HTTP/2 gave that up. Raise the loss slider far enough and HTTP/1.1 finishes first — not because it is a better protocol, but because it is more aggressive with the network. That was a genuine argument during HTTP/2's design, and this lab reproduces it rather than hiding it.

Head-of-line blocking, in one paragraph

HTTP/1.1 blocks at the protocol

A connection can only have one request outstanding, so request two waits for response one to finish arriving. Six connections means six of those queues. The fix was more connections, which cost more handshakes and more DNS.

HTTP/2 blocks at the transport

All the streams are multiplexed, so nothing queues at the protocol level. But TCP delivers bytes strictly in order: when a segment is lost, everything that arrived after it sits in the kernel buffer, undelivered, until the retransmit lands. Every stream stops, including the ones that lost nothing. In the picture that is the red band across all the rows at once.

HTTP/3 does not block across streams

QUIC numbers packets and tracks stream offsets separately, so a gap in one stream is not a gap in another. The red band covers one row. It is the same link, the same losses and the same congestion response — the only difference is who has to wait.

What none of them fix

Congestion control. All three cut their sending rate when a packet is lost, because the network told them to and ignoring it is how you get congestion collapse. Loss costs throughput in every version, and no transport can make a lossy link a good one. The TCP lab shows that mechanism on its own.

What this simulation does not model

A simulation that hides its assumptions is a graphic, not an argument. Here are mine.

It is arithmetic, not a network

No socket is opened and no packet is sent. The link is a bandwidth number, a round-trip number and a loss probability, stepped four milliseconds at a time. The shapes are real; the milliseconds are illustrative.

A stall costs exactly one round trip

When a packet is lost, the affected scope stops dead for one RTT. That overstates the cost on a fast link, where real TCP keeps sending until the receive window fills. It understates it whenever loss arrives in bursts, or when a retransmission timeout fires instead of a fast retransmit — those cost far more. The error runs in both directions and I have not tuned it to flatter anybody.

Congestion control is one simple loop

Slow start, then one more segment per round trip, then halve on a congestion event with one reduction per RTT. That is roughly Reno. Real stacks run CUBIC or BBR, which recover differently and would change the numbers. Queueing, buffer bloat and active queue management are not modelled at all.

HPACK is exact, except for Huffman

The static table indices, the integer prefix encoding, the entry sizing and the eviction are all as RFC 7541 specifies. The literals are sent uncompressed, which HPACK allows, so the literal bytes are around a fifth larger than a real encoder would send. Nothing changes for the indexed fields, which are what the view is about. HTTP/3 uses QPACK rather than HPACK — the same idea, rearranged so a lost packet cannot block header decoding.

The page model is simplified

One document, then everything it references, discovered all at once. Real pages discover resources in waves, run scripts that fetch more, and hit caches. There is no server push, no early hints, no preload scanner and no CDN. Priority weights are approximately the ones Chrome uses, not exactly.

HTTP/3 is not always faster

On a clean link the win is about one handshake round trip. UDP is rate-limited or blocked outright on some networks, and QUIC does its work in userspace rather than in the kernel, which costs measurably more CPU per byte. If you want to know whether it helps your site, measure your site — drop a real HAR file into the HAR analyser rather than trusting this.

Questions people ask

Is this a real network connection?
No. It is a simulation running as arithmetic in your browser. No socket is opened, no packet is sent, and the only real HTTP involved is the request that delivered this page. Move a slider and the three runs are recomputed from scratch; that is all it is doing.
Why does HTTP/2 fall apart when I raise the loss slider?
Because HTTP/2 multiplexed its streams on top of a single TCP connection, and TCP delivers one ordered byte stream. When a segment goes missing, TCP will not hand the application anything that comes after the hole - not for the stream that lost the packet, and not for the fifteen that did not. So one lost packet freezes every stream until the retransmit arrives. That is TCP head-of-line blocking, it cannot be fixed above the transport, and it is the entire reason HTTP/3 exists.
Is HTTP/3 always faster?
No, and this lab will show you that if you look. On a clean link HTTP/3 is ahead by about one round trip of handshake and very little else. Under loss it is clearly better than HTTP/2, but it is not immune: QUIC runs congestion control too, so a lost packet still cuts its sending window. UDP is also deprioritised or blocked outright on some networks, and QUIC does more work in userspace, which costs CPU. It is a real improvement, not magic.
Why does HTTP/1.1 sometimes beat HTTP/2 here?
Because six connections have six congestion windows and six independent recoveries, and one connection has one. Under loss that is a large advantage, and it is a real one that was argued about at length when HTTP/2 was young. HTTP/2 trades it for multiplexing, header compression and a single handshake, which is the right trade on most links and the wrong one on a bad mobile connection.
Are the HPACK byte counts real?
Yes, with one stated exception. The encoder uses the real RFC 7541 static table indices, real integer prefix encoding, and a dynamic table with real entry sizing of name plus value plus 32 bytes and real eviction at the table limit. What it does not do is Huffman-code the literal values, which HPACK permits - the H bit is simply zero. Huffman would take roughly a fifth more off the literals and nothing at all off the indexed fields, and the indexed fields are the point.
How accurate is the simulation?
It is calibrated to show the mechanism, not to predict your numbers. A lost packet stops the affected scope dead for one round trip, which overstates the cost on a fast link because real TCP keeps sending until the receive window fills, and understates it whenever loss arrives in bursts or a retransmission timeout fires. Queueing, buffer bloat, server push, TLS session tickets and CDN behaviour are not modelled at all. Treat the shapes as true and the milliseconds as illustrative.
Is anything uploaded?
No. Every round trip and every byte counted here is computed locally, and the page makes no network request of its own.
