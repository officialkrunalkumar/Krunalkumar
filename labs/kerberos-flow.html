Kerberos flow and attacks

Walk the exchange from AS-REQ to AP-REP, then attack it. The one to run first is Kerberoasting — because it is not an exploit. No bug is triggered and nothing is bypassed: a domain user asks the KDC for a service ticket, which is exactly what the protocol is for, and gets back a blob encrypted with the service account’s password. Run it as RC4, then as AES256, and read the cost-per-guess line both times. That one number is the whole argument for disabling RC4.

What the grade is made of

        

        

          

            
Kerberoasting is not an exploit

            
That is the thing worth internalising. Any authenticated domain user may request a ticket to any service, because deciding who may use a service is the service’s job and not the KDC’s. The request is normal, logs as event 4769 alongside thousands of legitimate ones, and hands over a blob encrypted with the service account’s password. The attack happens later, offline, on a machine you do not control.

          

          

            
The encryption type is the whole argument

            
With RC4 the key is the NT hash: one MD4 of the password, unsalted, uniterated. With AES256 each guess costs 4096 rounds of PBKDF2 — roughly ten thousand times the work. Same attack, same request, the difference between an afternoon and a year. And the client picks the etype in the request, so AES only helps once RC4 is actually refused.

          

          

            
Golden and Silver differ in what you can see

            
A Golden Ticket forges a TGT with the KRBTGT key, so there is no AS-REQ and event 4768 never fires — the domain first sees a valid ticket it has no record of issuing. A Silver Ticket forges a service ticket and never touches the domain controller at all, so there is no 4768 and no 4769. Smaller blast radius, almost no evidence.

          

          

            
The fixes are named, and so are the fake ones

            
Every mode ends with what actually works. Group Managed Service Accounts rather than “use a strong password”. Two KRBTGT resets with a real gap between them, because one leaves every forged ticket working. Tiering for pass-the-ticket, because it is the only control that genuinely stops it and it is organisational rather than technical.

          

        

      


      

        

          
Questions people ask

        

          

            Why can any user request a ticket for any service?
            
Because Kerberos separates authentication from authorisation on purpose. The KDC's job is to prove who you are; deciding whether you may use a particular service belongs to that service, which checks the PAC in the ticket you present. So the KDC will issue a service ticket to any authenticated principal that asks. That design is what makes Kerberos scale, and it is also exactly why Kerberoasting works without any bug being involved.

          

          

            Does disabling RC4 stop Kerberoasting?
            
No, it makes it about ten thousand times more expensive per password guess, which is usually enough. The request still succeeds and the blob still comes back; it is just derived with 4096 rounds of PBKDF2 instead of a single unsalted MD4. The complete fix is Group Managed Service Accounts, whose 240-character machine-generated passwords are not guessable at any cost.

          

          

            Why must the KRBTGT password be reset twice?
            
Because Active Directory keeps the previous KRBTGT key so that tickets already in flight keep working. One reset therefore leaves every forged Golden Ticket valid. You need two resets with a gap longer than the maximum ticket lifetime between them — and the gap matters as much as the second reset, since doing both back to back breaks live sessions domain-wide and still leaves a window open.

          

          

            Why is a Silver Ticket harder to detect than a Golden one?
            
Because it never reaches the domain controller. A service validates a ticket entirely by itself, using its own account key, without consulting the KDC — that is what makes Kerberos scale. So a forged service ticket produces no 4768 and no 4769: there is nothing for the domain controller to log because nothing was requested of it. Host-based logging on the service itself is the only place it appears.

          

          

            Does this tool touch my domain?
            
No. There is no KDC here, no LDAP query and no network code on the page at all. Every message is constructed in your browser from RFC 4120. It also means the tool cannot tell you which of your own accounts are roastable — that needs a query against your own directory, from a machine joined to it.
