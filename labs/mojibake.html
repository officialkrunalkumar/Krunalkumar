Mojibake repair

Text that arrives as CafÃ© or â€œ or ├⌐ is not damaged. It is the right bytes read through the wrong table, which is why it can usually be put back exactly. Paste some in and this names the wrong table, scores how sure it is, and hands you an ordered repair chain you can walk one step at a time — with the bytes on screen at every stage, because the bytes are the evidence and the glyphs are only the symptom.

  • Windows-1252, Latin-1, CP437, KOI8-R
  • Double encoding, counted in rounds
  • Stray and mid-file byte order marks
  • Every hypothesis scored, and the score broken down
  • U+FFFD called lossy, never faked

Before you start

This tool runs entirely inside your browser. Nothing you paste or drop here is uploaded, logged or stored — which for security work is the whole point, not a footnote.

What it does not do

  • No uploads — there is no server to upload to
  • Four charsets are tried, and all four are named
  • U+FFFD is never repaired — those bytes are already gone
  • The named-entity table is partial; numeric references are complete
  • Input is capped at 20,000 characters so the page stays responsive

Why that matters here

  • Broken customer data stays on your machine
  • Nothing you paste ever appears in your Network tab
  • No account, no history, nothing saved
  • Works with no internet once the page is cached
  • Free, permanently

    What is actually wrong with the text
    
        
    
        
    
          
    
            
    It is not corruption
    
            
    Mojibake is a correct decode of the right bytes under the wrong table. The bytes for “café” in UTF-8 are 43 61 66 C3 A9; read as Windows-1252 those last two bytes are Ã and ©, so you see CafÃ©. Nothing was lost, so encoding the glyphs back to bytes and decoding them properly gives the original back exactly. That is what this tool does, and it shows you the bytes at each stage so you can check rather than trust.
    
          
    
          
    
            
    0x80 to 0x9F is the whole argument
    
            
    Latin-1 leaves that byte range as C1 control characters. Windows-1252 fills it with the curly quotes, the two dashes, the euro sign and the ellipsis — exactly the characters people paste. Five slots (81 8D 8F 90 9D) are undefined in Microsoft’s original code page, and U+201D, the closing curly quote, encodes to E2 80 9D. That is why â€ turns up so often, and why the byte that ends it goes missing in any round trip that treats the two tables as interchangeable.
    
          
    
          
    
            
    U+FFFD is a receipt, not damage
    
            
    The replacement character � means a decoder met bytes it could not read and threw them away. What reaches you is the note it left behind, not the bytes. There is nothing to reverse, and any tool that offers to “fix” one is guessing at content. This one says LOSSY, gives the positions, and tells you to go back to the file from before that decode ran.
    
          
    
          
    
            
    A byte order mark in the middle of a file
    
            
    A BOM at offset zero is a nuisance you can strip. A BOM three lines down is evidence: it means two files were joined byte-for-byte by something that never looked at them, which is the ordinary result of concatenating two exports that each start with one. The tool reports the offsets, because the mid-file copy is the one that breaks a parser a dozen steps downstream from where it was introduced.
    
          
    
        
    
      
    

      
    
        
    
          
    Questions people ask
    
        
    
          
    
            Is the text I paste uploaded anywhere?
            
    No. The character tables, the decoder and the scoring are all in one JavaScript file that runs in your tab. There is no network call of any kind. Broken text is usually real customer data — names, addresses, subject lines — which is exactly the sort of thing that should not be pasted into an unknown server to be tidied up.
    
          
    
          
    
            What is the difference between REVERSIBLE and LOSSY here?
            
    Reversible means every original byte is still present in what you pasted, just read through the wrong table, so the repair is exact rather than a reconstruction. A mis-decode, a doubled entity and a stray BOM are all reversible. LOSSY means bytes were discarded before you ever saw the text — that is what U+FFFD marks — and no amount of processing brings them back. The report labels every finding one way or the other and never blurs the two.
    
          
    
          
    
            What does the confidence number actually mean?
            
    It is a score over four measured signals, and all four are printed alongside it: whether every character maps to a byte in that charset, whether those bytes pass a strict UTF-8 decode, how far the count of damage markers fell, and whether any marker is left. It caps at 99 on purpose. Nothing here can prove the result is what the author typed, only that one wrong-decode story explains every byte.
    
          
    
          
    
            Why does it bother with CP437 and KOI8-R?
            
    Because they still turn up. CP437 is the IBM PC character set and remains the default code page of a great many Windows consoles, so exports from old tooling arrive looking like line-drawing art. KOI8-R is what a large amount of archived Russian mail is stored in. They are rarer than Windows-1252 and are tried after it, but they are tried properly, with their own tables, not guessed at.
    
          
    
          
    
            It did not repair my text. What now?
            
    Read the rejection reasons in the hypothesis table — each one names the character or the byte that ruled that charset out, which is often more useful than a repair would have been. If the answer is a replacement character, the text cannot be recovered from here and you need the file from before the bad decode. If it is a charset this tool does not carry, it says so rather than forcing a wrong answer onto your text.
    
          
    
          
    
            Can it break text that was fine to begin with?
            
    A whole-text repair is only accepted if every character maps to a byte and those bytes pass a strict UTF-8 decode, which ordinary prose fails almost immediately — a lone é is byte E9, and E9 is not a valid UTF-8 sequence. The run-targeted mode is weaker, because it picks its own boundaries, so it scores lower, and it names the runs it repaired and the runs it refused — the first five of each, with a count of anything past that. Nothing is applied to your input until you press a button.
