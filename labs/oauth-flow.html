OAuth 2.0 flow simulator

Walk the authorization code flow step by step with real values — a real 32-byte verifier, a real S256 challenge computed by your browser’s own crypto. Then attack it. Steal the code with PKCE off and the attacker walks away with an access token; turn PKCE on and watch the token endpoint refuse. Every OAuth diagram shows the happy path, which is the one nobody gets wrong.

  • Real PKCE values, not placeholders
  • Five attacks, each with what stops it
  • Audits an authorize URL you paste
  • RFC 6749, 7636, 9207 and OAuth 2.1
  • No authorization server, nothing fetched

Before you start

This tool runs entirely inside your browser. Nothing you paste or drop here is uploaded, logged or stored — which for security work is the whole point, not a footnote.

What it does not do

  • No uploads — there is no server to upload to
  • No account, no history, nothing saved
  • No requests to any authorization server
  • No OAuth client registered anywhere

Why that matters here

  • Evidence files stay on your machine
  • A token or key you paste is never transmitted
  • A client_id or URL you paste never leaves the tab
  • Works with no internet once the page is cached
  • Free, permanently

What the grade is made of

        

        

          

            
The values are real

            
The code_verifier is 32 bytes from crypto.getRandomValues. The challenge is base64url(SHA‑256(verifier)), computed by crypto.subtle in your tab. Copy both out and check the digest yourself — it will match. Only the code and the tokens are invented, because inventing those is exactly what an authorization server does.

          

          

            
The attacks are the lesson

            
The happy path is the path nobody gets wrong. Run the stolen-code attack with PKCE off and the attacker receives tokens; switch to S256 and the same request returns invalid_grant. That single comparison is the entire argument for PKCE, and it is far more convincing than a paragraph claiming it.

          

          

            
What PKCE does not fix

            
Three of the five attacks here survive it. A loosely matched redirect_uri delivers the code to a page running your own client code, which can often read the verifier too. A provider mix-up has the client hand its verifier to the attacker willingly. Code replay needs the server to burn the code. PKCE is one control, not a posture.

          

          

            
Audit mode reads a URL, not your server

            
Paste the authorize request your application really builds and it flags implicit flow, absent or plain PKCE, missing state, cleartext or wildcard redirects, and secrets that should never travel through a browser. It cannot tell you whether your server enforces any of it — that lives in code this page cannot see, and the output says so rather than implying coverage it lacks.

          

        

      


      

        

          
Questions people ask

        

          

            What is PKCE and why does OAuth need it?
            
PKCE (RFC 7636) makes the client prove it started the flow. It generates a random code_verifier, sends only base64url(SHA-256(verifier)) as the code_challenge, then presents the verifier when exchanging the code. An attacker who steals the authorization code cannot exchange it, because the code alone no longer proves anything. Run the stolen-code attack with PKCE on and then off — the difference is one line of output.

          

          

            Do I still need state if I use PKCE?
            
Yes, and OAuth 2.1 expects both. They answer different questions. PKCE proves the client redeeming the code is the client that requested it. state binds the callback to the browser session that started the flow, which is what stops login CSRF, and it carries your own return-to-page context. It must be compared server-side against the session, not merely echoed back from the URL.

          

          

            Why is the implicit flow discouraged?
            
response_type=token returns the access token in the URL fragment, so it lands in browser history, in the Referer of anything the page loads, and within reach of every script on the page. There is no client authentication and no code exchange in which to check anything. It was a workaround for browsers without CORS, and it was removed in OAuth 2.1.

          

          

            Why must redirect_uri be matched exactly?
            
Because the authorization server sends the code wherever it points. Prefix matching lets an attacker append their own host; a subdomain wildcard turns one dangling DNS record into code theft; an unchecked query parameter on the callback becomes an open redirect. Exact full-string comparison against the registered value is the only safe rule — and PKCE does not rescue you here, because the code is delivered to a page running your own client code.

          

          

            Does this tool test my authorization server?
            
No. It reasons about a URL and about the specification, entirely inside your browser. It can tell you a request omits PKCE or carries a cleartext redirect. It cannot tell you whether your server would have rejected it anyway, whether redirect_uri is registered exactly, or whether state is really compared. Those live in code this page cannot see.
