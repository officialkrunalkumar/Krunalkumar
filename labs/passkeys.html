Passkey and WebAuthn explorer

Passkeys are usually explained with a diagram. This page does not have one. It calls the browser’s real WebAuthn API against this origin, registers an actual credential on your actual authenticator, and then takes the response apart byte by byte — the CBOR, the flags, the AAGUID, the public key, and a signature that gets verified in front of you. Then it shows you why a lookalike site could not have used any of it.

  • Real navigator.credentials calls
  • CBOR and COSE decoded here
  • Every flag bit named
  • Signature verified in the tab
  • No server, nothing uploaded

Before you start

This tool runs entirely inside your browser. Nothing you paste or drop here is uploaded, logged or stored — which for security work is the whole point, not a footnote.

What it does not do

  • No uploads — there is no server to upload to
  • No account, no history, nothing sent
  • No private key is ever exposed — the API does not return one
  • Not a login. The passkey you make here protects nothing

Why that matters here

  • Evidence files stay on your machine
  • A token or key you paste is never transmitted
  • Nothing you paste ever appears in your Network tab
  • Works with no internet once the page is cached
  • Free, permanently

Why a lookalike site cannot use this passkey

Sign in above, and this takes the signature your authenticator really made, changes one string inside the signed data — the origin — and checks it again. Nothing else is touched. It is the same public key, the same authenticator data, the same signature.

What happened when you approved that prompt

The key pair is made where you cannot reach it

The authenticator generates two halves and keeps the private one. There is no WebAuthn call that returns it, not for the site and not for the page you are reading — which is why a breach of a passkey database yields a list of public keys and no way to sign with any of them. Compare that with a password file, where the whole value of the theft is that the stolen thing is the thing you type.

The challenge is what stops a replay

Thirty-two random bytes, different every time, signed along with everything else. A server issues one, remembers it, and refuses a response echoing anything else. This page generates its own because there is no server, which is fine for watching the mechanism and worth nothing as a security control — a point the tool repeats rather than glosses over.

clientDataJSON is written by the browser, not the page

It carries the type of ceremony, the challenge echoed back, and the origin the browser actually loaded. A page cannot set that origin, cannot read another tab’s, and cannot forge it. Its SHA-256 is concatenated onto the authenticator data before signing, so the origin is inside the signature rather than alongside it.

Attestation answers a different question

Registration can carry a statement about the make and model of the authenticator, signed by a manufacturer key. That is an enterprise control — only these approved security keys — and a privacy cost for everyone else. Most consumer deployments ask for none, which is why the AAGUID you see is usually sixteen zero bytes.

There is a second thing passkeys quietly fix. “We do not store your password” is a claim that is usually false as stated — a hash is still password-derived data, and a stolen database is a cracking problem rather than a dead end. With a passkey the server holds only a public key and there is no shared secret to steal, which makes the sentence true for the first time.

The part that actually beats phishing

Two independent walls, and it is worth knowing which one is doing the work.

Wall one: the browser will not lie about who is asking

A page may only claim an RP ID equal to its own domain or a registrable parent of it. Ask for anything else and the call is refused before any authenticator is contacted and before any prompt appears. Press Try a foreign RP ID in the toolbar and watch it happen. A phishing page never gets as far as a human decision, which is the difference between a control and a warning.

Wall two: the origin is inside the signed bytes

The signature covers the authenticator data concatenated with SHA-256 of the client data, and the client data contains the origin. Change one character of it and the hash changes, so the signature stops verifying. The demonstration in the tool does exactly that to a real signature, and you can watch the verification flip from valid to invalid.

There is nothing to read out loud

The reason a real-time proxy defeats a one-time code is that the code does not know which site asked for it. You read six digits off a phone, someone relays them inside thirty seconds, and the expiry never helps. A passkey has no such value: the assertion is bound to the origin that requested it, so relaying it produces a signature the real site rejects.

What this does not fix

It ends credential phishing. It does not end account takeover. A session cookie stolen after a legitimate sign-in still works, malware on the device is still malware, and the account recovery flow behind the passkey — an email link, a support agent, a code by text — is usually the weakest thing in the system. Passkeys move the problem; they do not delete it.

Discoverable, device bound, synced

Three words that decide what happens the day you lose the phone.

Discoverable or not

A discoverable credential is stored on the authenticator with a user handle, so the browser can find it knowing only the site. That is what makes a sign-in button with no username field possible. A non-discoverable one has to be named in allowCredentials, which means the site must already know who you claim to be. The tool lets you try both and shows the request either way.

User verification is what makes it two factors

The UP bit says a human touched the authenticator. The UV bit says the authenticator checked which human — a PIN, a fingerprint, a face. Only UV turns possession into possession plus something else. A site that sets user verification to discouraged and then calls the result multi-factor is telling itself a story.

BE and BS, in plain language

BE means this credential is the kind that can be copied to an account. BS means it currently has been. Both set is a synced passkey: it appears on your next device and the security of the passkey becomes the security of the Apple, Google, Microsoft or password-manager account behind it. Both clear is device bound: stronger, and gone with the device.

Recovery is where accounts really fall over

A device-bound passkey with no second enrolment is one dropped phone away from a support ticket, and support tickets are where social engineering lives. Enrol two authenticators, or accept syncing and protect the account it syncs through properly. The failure mode of good authentication is almost always the recovery path, not the algorithm.

What this page does not do, and a real deployment must

The challenge comes from the page

There is no server, so the random bytes are generated here and compared here. A relying party issues the challenge, stores it against the session, gives it a short lifetime and refuses to accept it twice. Without that, an assertion captured once could be presented again, and every other check in the list would still pass.

The verification proves less than it looks

The signature check in the tool is genuine arithmetic against a real public key, and it runs in the same tab as the code that decided what to sign. A server also checks that the origin string is exactly its own, that the RP ID hash matches, that the user was verified if it required that, and that the sign counter has not gone backwards.

localStorage is not a credential store

The public key sits in this browser under one key so the page can verify a signature later. A real deployment writes it into a row against your account with the credential ID, the sign counter and the transports, and treats the row as public information — because that is what it is.

Attestation is decoded, not validated

If you ask for direct attestation the tool shows you the format, the statement keys and the certificate lengths. It does not verify the chain, because that needs vendor root certificates fetched over the network, and this page does not make network requests. Saying so is more useful than a green tick that means nothing.

Questions people ask

Is anything about my passkey sent to a server?
No, and there is no server here to send it to. The challenge is generated in this page, the public key is kept in this browser's localStorage, and the signature is verified in this tab with Web Crypto. Open your Network tab and press every button on this page; nothing carrying anything you did will appear. The private key was never available to send in the first place, because no WebAuthn call returns one.
Is this a real passkey or a simulation?
Real. The page calls navigator.credentials.create and navigator.credentials.get, your own authenticator answers, and every structure on screen is decoded from what it returned. The one simulated thing is the lookalike origin, because a browser will not let a page produce a genuine assertion for a domain it is not served from, and that refusal is exactly the lesson.
Can I use this passkey to sign in to something else?
No. It is scoped to this site's RP ID, so no other site will ever be offered it. It also protects nothing here, because there is no account behind it and no server checking anything. It exists so you can watch the machinery, and then delete it in whichever password manager or security key stored it.
Why did the AAGUID come back as all zeroes?
Because the authenticator declined to identify its model, which is the normal and privacy preserving answer. An identifier for the make and model attached to every registration would be a tracking signal, so platform authenticators and synced passkey providers usually return zeroes unless a site asks for attestation and the platform agrees to supply it.
What do the BE and BS flags actually change for me?
They tell you where the private key lives. BE set means the credential is the kind that can be synced to an account; BS set means it currently is. A synced passkey survives a lost phone and inherits the security of the account it syncs through. A device bound one does not survive the phone, which is why anyone relying on a hardware key is told to enrol a second one.
