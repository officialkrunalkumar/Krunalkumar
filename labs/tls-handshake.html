The TLS handshake, message by message

Everyone knows the padlock means TLS. Far fewer people could say which message the encryption actually starts at — and most published diagrams put it in the wrong place. Step a TLS 1.3 handshake one message at a time with TLS 1.2 running alongside, take the ClientHello apart byte by byte, watch a real HKDF key schedule produce the traffic secrets, then break the handshake on purpose and read the exact alert the client sends back.

  • Which messages are encrypted, and from where
  • Every ClientHello extension, with its real bytes
  • HKDF-Expand-Label actually computed, not drawn
  • Expired, mismatched, downgraded — and the alert for each
  • 0-RTT, and the replay risk it is paid for with

The thing most handshake diagrams get wrong

Encryption starts one message after ServerHello

The usual picture puts a padlock next to “Finished”, as though the handshake negotiates in the open and only then closes the door. In TLS 1.3 that is wrong by four messages. Both sides can compute the handshake traffic secrets the instant ServerHello lands, because the key shares and the transcript are all they need — so EncryptedExtensions, the certificate, CertificateVerify and Finished are all already encrypted. Every row in the ladder carries the key it travels under, taken from the model rather than drawn on, so the two versions cannot quietly disagree with each other.

The certificate is the row worth comparing

In TLS 1.2 the certificate chain is plaintext. Anyone with a tap on the path learns which site you are talking to for free, whatever else they cannot read. TLS 1.3 moved it behind the handshake keys, which is one of the largest practical privacy changes in the protocol’s history — and it is undercut in practice by the server name still travelling in the clear a message earlier. Switch modes with the same failure selected and watch that one row change colour.

In TLS 1.3, even the failure is private

Select the expired certificate and run it in both versions. In TLS 1.2 the alert leaves before any keys exist, so an observer sees a plaintext record saying fatal, certificate_expired — the failure and its reason are public. In TLS 1.3 handshake keys already exist by the time the client gives up, so the alert is encrypted inside a record that claims on the outside to be ordinary application data. The tool shows both, byte for byte.

Some records are pure theatre

A TLS 1.3 handshake still contains a ChangeCipherSpec that means nothing and a 32-byte session ID for a protocol with no session IDs. Both exist so the exchange looks like TLS 1.2 to middleboxes that would otherwise drop it. RFC 8446 calls this compatibility mode and requires the receiver to ignore it. Reading a capture properly means knowing which records are load-bearing and which are costume.

How to read the four tabs

The handshake — and how to break it

Step or play through the messages. Click any one to pin it, and the panel below gives you what it contains, what it is for, and what somebody watching the wire actually sees at that moment. The failure picker is the part worth spending time in: an expired certificate, a name that does not match, a forced downgrade and a cipher list with no overlap each stop the handshake where a real client would stop it and show the alert record byte by byte. One of those alerts is honestly ambiguous and the tool says so instead of inventing a rule.

The ClientHello, built rather than pasted

Every field is constructed from the structure, so typing a longer server name really does move the length fields above it. Click any extension for its hex dump and a table of what each run of bytes means. The extensions are where the interesting history lives: a version field frozen at TLS 1.2 forever, a session ID that is deliberate noise, a public key sent on spec before the server has said a word, and one plaintext field that tells everyone on the path exactly where you are going.

The key schedule is arithmetic, not a picture

Every secret is HMAC-SHA-256 computed in your browser as RFC 8446 section 7.1 specifies, over transcript hashes that are genuine SHA-256 digests of the sample messages this lab builds. The Early Secret and the derived value after it match the constants published in RFC 8448, which is the check that the label encoding is right. Edit the shared secret and watch every line below change completely. The inputs are samples and the page says so on every panel — the ladder is correct, and none of these numbers came from a real connection.

Round trips, including the one you can skip

Set your own latency and see where the time actually goes: DNS, then TCP, then TLS, then the request. TLS 1.3 saves one round trip over 1.2 — unless the client’s key-share guess was wrong, in which case HelloRetryRequest hands the saving straight back. 0-RTT removes the last one entirely and charges for it in replay risk and forward secrecy, both of which are spelled out rather than mentioned.

What this cannot tell you

The limits are as much the point as the walkthrough.

It is a model, not a client

There is no TLS implementation in this page and it opens no connection. It cannot test your server, cannot tell you which version a site negotiates, and cannot verify anybody’s certificate. If you want to know what a real connection did, capture it and read the capture — the PCAP analyzer takes the file. If you want to know what is in a certificate you already have, that is the certificate decoder.

The secrets are samples, and deliberately so

The ECDHE shared secret, the randoms, the public keys and the certificate body are all invented, and the certificate body is a short stand-in rather than real DER. That is why the key schedule can be shown at all: real key material on a public page would be either fake or a disaster. The derivation is exact and the inputs are not, and no output here will match a capture you own.

Only the SHA-256 suites are computed

TLS_AES_128_GCM_SHA256 and TLS_CHACHA20_POLY1305_SHA256 both run the SHA-256 ladder, so both are computed properly. TLS_AES_256_GCM_SHA384 runs the identical schedule with SHA-384 and 48-byte secrets, and it is not implemented here rather than being faked with the wrong hash and a relabelled output.

One alert code is genuinely uncertain

There is no alert in the specification that means “wrong hostname”. OpenSSL maps that failure to bad_certificate(42), other stacks send certificate_unknown(46), and browsers frequently close the connection and show their own interstitial instead. The tool shows the most common code and says plainly that it is a hint about which library you are talking to rather than a diagnosis. certificate_expired(45) and handshake_failure(40) have no such ambiguity.

Questions people ask

Does this lab talk to a server or read my real TLS traffic?
Neither. There is no TLS client in this page and it opens no connection of any kind. It is a model of the protocol built from the specification, so it can show you how a handshake is shaped and it can tell you nothing whatsoever about a real server. If you want to inspect an actual connection, that is what a packet capture and the PCAP analyzer are for.
Why is the certificate encrypted in TLS 1.3 but not in TLS 1.2?
Because TLS 1.3 splits the server response in two. ServerHello carries only what is needed to derive keys, and the moment it lands both sides can compute the handshake traffic secrets from the key shares and the transcript. Everything after that point, the certificate chain included, travels under those keys. TLS 1.2 could not do this because the client had not sent any key material yet when the certificate went out, so there was nothing to encrypt it with.
If TLS 1.3 encrypts so much, why can my ISP still see which sites I visit?
Because the server name extension in the ClientHello is plaintext, and it has to be: the server needs to know which certificate to present before there is any key to hide the question under. That single field is what domain-level blocking and logging are built on. Encrypted Client Hello fixes it by sealing the real ClientHello to a public key published in DNS, and it needs the server, the browser and a private DNS lookup all lined up, which is why it is not yet the default anywhere.
Are the keys on the key schedule tab real?
The arithmetic is real and the inputs are not. Every value is HMAC-SHA-256 computed in your browser exactly as RFC 8446 section 7.1 specifies, and the transcript hashes are genuine SHA-256 digests of the sample handshake messages this lab builds. Two of the values, the Early Secret with no PSK and the derived secret that follows it, match the constants published in RFC 8448, which is the check that confirms the label encoding is right. What is invented is the ECDHE shared secret, the randoms and the stand-in certificate body, so nothing here will match a capture you own.
Is 0-RTT safe to turn on?
It is a trade, and the honest answer is that it depends on what the first request does. Early data is replayable, because nothing fresh from the server covers it, and RFC 8446 says outright that the available defences are incomplete across a cluster of servers. It also has no forward secrecy, since it is keyed from the resumption secret rather than a fresh exchange. For an idempotent GET on a slow link it is a large win. For anything that changes state it is a bad idea, which is why browsers and servers both restrict it.
Why does TLS 1.3 still send a ChangeCipherSpec that does nothing?
Middlebox compatibility. Enough deployed equipment had learned the exact shape of a TLS 1.2 handshake that a connection which did not look like one got dropped, so TLS 1.3 keeps a meaningless ChangeCipherSpec record and a random legacy session ID purely to look familiar on the wire. RFC 8446 requires receivers to ignore it. It is one of the more honest admissions in a modern protocol specification, and it is why reading a capture means knowing which records are decorative.
Is TLS 1.2 broken?
No, and saying so would be the kind of overstatement this site tries to avoid. A TLS 1.2 connection with an ECDHE key exchange, an AEAD cipher suite and the extended master secret extension is sound today. What TLS 1.3 did was remove the option to configure it badly: static RSA, renegotiation, compression, CBC constructions and hundreds of weak suites are gone rather than merely discouraged. The privacy gain from encrypting the certificate and the alerts is real and separate from that.
