TOTP generator and verifier

Most people assume the six digits in their authenticator app arrive from somewhere. They do not. The code is an HMAC over a number both sides work out from the clock, cut down to six digits by a rule from RFC 4226. Every one of those steps is on this page, updating as you watch.

  • HMAC-SHA-1, SHA-256 and SHA-512
  • Every intermediate value, live
  • Clock-skew slider and window check
  • otpauth URI and QR, drawn here
  • Checked against the RFC vectors

Before you start

This tool runs entirely inside your browser. Nothing you paste or drop here is uploaded, logged or stored — which for security work is the whole point, not a footnote.

What it does not do

  • No uploads — there is no server to upload to
  • No account, no history, nothing saved
  • No secret is stored, logged or transmitted
  • Not a replacement for an authenticator app — this is for understanding the mechanism

Why that matters here

  • A token or key you paste is never transmitted

  • Works with no internet once the page is cached

    How that number was derived

    That string is the whole enrolment. When a site shows you a QR to set up two-factor authentication, this is what is inside it: a label, the Base32 secret, and the three parameters that have to match — algorithm, digits and period. Change any of them above and watch the URI and the square change with it.

    The square is drawn here, in the page, by a QR encoder written for this tool. That matters more than it sounds: almost every online QR generator builds the image on a server, which means handing your two-factor secret to a stranger in order to look at it. Nothing here leaves the tab.

    The secret the page starts with is the one every piece of TOTP documentation uses, so you can compare the codes against any other implementation. It is also 80 bits and completely public, which is why the field flags it — press Generate a secret for a real 160-bit one.

    What the six digits actually are

    There is nothing to fetch

    Your phone and the server share one secret, agreed once at enrolment. Both divide the current Unix time by thirty to get the same integer, both compute an HMAC of it with that secret, and both cut the result down the same way. Put a phone in aeroplane mode for a year and it still produces the right code, because it was never asking anybody.

    Why the code moves around inside the HMAC

    Dynamic truncation reads the last four bits of the digest, uses that as an offset, and takes the four bytes starting there. So the digits come from a different place in the MAC each step. A fixed slice would leak the same part of the output every time; this way an attacker collecting codes learns almost nothing about the rest of it.

    The window is a clock allowance, not a security margin

    Servers accept the step before and after because phones drift and people type slowly. That is a usability decision with a cost: a code accepted with a ±1 window is live for up to ninety seconds, not thirty. Widening it further to reduce support tickets is the wrong lever — fix the clock instead.

    Replay is the server’s job, not the algorithm’s

    Nothing in RFC 6238 stops the same code being used twice. The server has to remember the last counter it accepted for that user and refuse anything at or below it. Plenty of implementations skip that, which is how a code read over somebody’s shoulder still works thirty seconds later on a different device.

    Why TOTP beats SMS, and what still beats TOTP

    Both halves of this are worth saying out loud. TOTP is a genuine improvement over text messages, and it is not the end of the story.

    SMS is somebody else’s network

    A code sent by text has to travel: through your carrier, through the interconnect, onto whichever SIM currently answers to your number. That gives you SIM swap, port-out fraud, SS7 interception, and a support agent at a phone company who can be talked into a transfer. TOTP has no delivery step at all. After enrolment nothing about the code ever crosses a network, so there is nothing to intercept and nobody to social-engineer.

    Where TOTP still loses: the real-time relay

    A phishing proxy sits on a lookalike domain and forwards everything to the real site as you type. You enter the password, it relays it; the real site asks for a code, it asks you; you read the code off your phone, it relays that too — well inside the thirty seconds — and keeps the session cookie that comes back. The expiry never helps, because the attacker is not waiting. This is not exotic; the tooling for it is off the shelf.

    Passkeys are the actual fix

    A passkey is a key pair bound to the origin it was created for. Signing in means signing a challenge from the site, and the browser will not sign one for a lookalike domain — not because it detects the phish, but because the wrong domain is simply not the same key. There is nothing to type, so nothing can be read aloud, screenshotted or relayed. That is a structural fix rather than a shorter window.

    What to do in the meantime

    Turn on passkeys where they are offered. Use TOTP everywhere else, in preference to SMS. And treat the recovery codes as exactly what they are — a copy of the secret in plain sight — because the usual way an account with good two-factor falls over is a recovery flow, not a broken algorithm.

    The longer version of this argument — why passkeys are a different kind of thing rather than a better password, what a real-time proxy actually does to a login, and what to do about passwords in the meantime — is written up separately.

    How I checked this, and what it does not do

    Against the published vectors

    The ten HOTP vectors in RFC 4226 Appendix D and all eighteen TOTP vectors in RFC 6238 Appendix B — six timestamps each for SHA-1, SHA-256 and SHA-512 — run in your browser when the page loads, and the toolbar shows the count. The hash implementations were also compared against a known-good library over several thousand random inputs while I was building this.

    The QR encoder

    Written for this page: byte mode, error correction level M, versions 1 to 10. I checked it by decoding its own output back with a separately written reader — format bits, mask, de-interleaving, Reed-Solomon syndromes, the lot — and by comparing the format and version information against the published tables. If a URI is too long for version 10 the tool says so rather than drawing a square that will not scan.

    The clock is your clock

    Everything here is computed from this device’s system time. If that is wrong, the codes are wrong in exactly the way a real authenticator would be, which is the honest behaviour. The skew slider does not change your clock; it shows you what a device with that error would be producing right now.

    What a real server has to do that this does not

    Verification here compares in constant time, which a server must also do. It does not do the rest of the server’s job: rate-limiting attempts, refusing a counter it has already accepted, and storing the secret encrypted rather than in a column anyone with read access can select.

    Questions people ask

    Is my secret sent anywhere?
    No. The secret is decoded and the HMAC computed in this tab, and the QR is drawn on a canvas here rather than fetched from a chart service - which is how most online QR generators work, and the reason they end up holding your secret. There is no server in this tool and no request carrying anything you type is ever made. Open the Network tab and watch.
    Did you actually check this against the RFC test vectors?
    Yes, and the page runs them in front of you. The toolbar shows the result of the ten HOTP vectors in RFC 4226 Appendix D and all eighteen TOTP vectors in RFC 6238 Appendix B, across SHA-1, SHA-256 and SHA-512. If one failed the toolbar would say so in red rather than quietly showing you wrong numbers. You can re-run them yourself: open the browser console and call TotpEngine.selfTest().
    Should I use this instead of an authenticator app?
    No. Use an authenticator app or a hardware key for accounts that matter. This page holds a secret in a text field so you can watch what happens to it, which is the right trade for understanding the mechanism and the wrong one for protecting an account.
    Why does the code here not match my phone?
    Almost always the clock. TOTP has no channel to correct a drifting device, so a phone half a minute out shows the next window's code - drag the skew slider and you can watch that happen. If the clock is right, check the algorithm, the digit count and the step: a service using SHA-256, eight digits or a sixty-second period will not match the defaults.
    If TOTP can be phished, is it worth turning on?
    Yes. It removes the entire class of attacks that work on a password alone: credential stuffing, password reuse, and anything that falls out of a breach dump. What it does not remove is somebody being walked through a convincing login page in real time. Passkeys remove that, because the browser will not sign for the wrong origin.
